---
title: "SATv2 による AWS の健康診断"
---

AWS アカウントがたくさんあり、それぞれ違う人が作ってきた会社では、「どこにどんな穴があるのか」を把握するだけで大変です。この章では、AWS が無償で公開している **SATv2** を使って、AWS 全体の「健康診断」をする方法を整理します。

## SATv2 とは

**SATv2（Self-Service Security Assessment Solution v2）** は、AWS Labs が GitHub で公開しているソリューションです（[awslabs/aws-security-assessment-solution](https://github.com/awslabs/aws-security-assessment-solution)）。オープンソースのセキュリティ診断ツール **Prowler** を、自分の AWS アカウントの中で動かし、**1 つのアカウント、または AWS Organizations 配下の全アカウント** を一度に診断します。

| 項目 | 内容 |
|---|---|
| 位置づけ | **ある時点の評価**（ポイントインタイム評価）。常時監視の道具ではない |
| 仕組み | CloudFormation で CodeBuild・S3・Lambda を作り、CodeBuild の中で Prowler を実行する |
| 権限 | 各アカウントに StackSet で **読み取り専用** の IAM ロールを配り、Prowler がそれを引き受けて診断する |
| 所要時間 | デプロイ 5 分程度、標準の診断も数分〜（リソース数による） |
| 費用 | 無料利用枠に収まるよう設計。超えても 1 回あたり 1 ドル未満の見込み（README より） |
| 出力 | アカウントごとの HTML レポート、CSV、JSON / OCSF JSON。オプションで Athena による全社集計とダッシュボード HTML |

AWS の「Security Health Improvement Program（SHIP）」というワークショップでも、最初のステップとして SATv2 による評価が使われています。また、2026 年には AWS の AI 開発環境 Kiro のスキルとして SATv2 の診断を実行する方法も紹介されています。

:::message
**なぜ Security Hub ではなく SATv2 から始めるのか**: Security Hub は常時監視のための仕組みで、全アカウントに展開して運用を始めるまでに時間がかかります。SATv2 は、何も入っていない状態の環境でも **数十分で全体像を出せる** ので、「まず現状を知る」「経営に穴の大きさを見せる」という Lv0 → Lv1 の最初の一歩に向いています。継続的な点検は、そのあと Security Hub の FSBP 標準などに引き継ぎます（README でもそう推奨されています）。
:::

## 診断の種類

| 種類 | 内容 | 使いどころ |
|---|---|---|
| Basic | CloudTrail・Config の有効化、開いたセキュリティグループ、ルートの MFA、公開 S3 など、基本的なチェックだけ | 最初の 1 回、経営への説明用 |
| **Intermediate**（既定） | 重大度「Critical」「High」のチェックすべて | 通常はこれ |
| Full | 650 以上のチェックすべて | Lv2 以降の詳細な点検 |

既定では、Lambda のコードや EC2 のユーザーデータなどの **中身を読んでシークレットを探すチェック（23 個）はスキップ** されます（`ExcludeSecretsChecks=true`）。中身をダウンロードせずに済み、レポートに機密情報が載るのも防げるためです。シークレットの検出は、GitHub のシークレットスキャン（9 章）など、別の手段で補います。

## 進め方

### 1. 準備

- 診断を実行するアカウント（**監査用 / セキュリティツール用アカウント** が適切）を決める
- 対象範囲（全アカウントか、一部の OU か）を決める
- 関係者に「読み取り専用で診断する」ことを事前に伝える

### 2. デプロイ（複数アカウントの場合）

1. 管理アカウントから、メンバーアカウント用の読み取りロール（`1-sat2-member-roles.yaml`）を **StackSet** で組織（または OU）に展開する。管理アカウント自体には StackSet が適用されないので、通常のスタックとして別途作る
2. 診断を実行するアカウントに、組織の情報を読む権限を与える（委任管理者の登録、または組織のリソースポリシー）
3. 診断を実行するアカウントで、本体のテンプレート（`2-sat2-codebuild-prowler.yaml`）を `MultiAccountScan=true` でデプロイする
4. 全社の集計が欲しければ `Reporting=true`、終了通知が欲しければ `EmailAddress` を指定する

手順の詳細とパラメーターは、必ず最新の README を確認してください。

### 3. 結果を読む

結果は S3 バケットに、実行日時ごとのフォルダで出力されます。

- `html/`: アカウントごとの HTML レポート。フィルタして優先順位づけができる
- `csv/`、`json/`、`ocsf-json/`: 機械処理用
- `reports/`: `Reporting=true` のときの全社集計 CSV とダッシュボード（`satv2-dashboard.html`）

:::message alert
**結果の扱いに注意**: レポートは「自社のどこに穴があるか」の一覧なので、それ自体が機密情報です。S3 の署名付き URL で共有するときは、URL に作成者の権限が乗ることと、有効期限に注意してください。社内でも共有範囲を絞ります。
:::

### 4. 優先順位をつける

結果は数百〜数千件になることが多いです。次の順番で見ていくと、手が止まりません。

1. **Critical / High で、インターネットから到達できるもの**（公開 S3、0.0.0.0/0 のセキュリティグループ、公開スナップショットなど）
2. **ID まわり**（ルートの MFA、ルートのアクセスキー、古いアクセスキー、管理者権限を持つ IAM ユーザー）
3. **検知とログ**（CloudTrail・GuardDuty・Config が無効なアカウント・リージョン）
4. それ以外の Critical / High
5. Medium 以下は、Lv2 以降で Security Hub の運用に引き継ぐ

アカウントごとの件数を一覧にすると、「放置されているアカウント」がはっきり見えます。責任者のいないアカウントは、削除するか、責任者を決めるかを経営判断にかけます。

### 5. 片付ける

SATv2 は「使ったら消す」前提のソリューションです。

- 本体のスタック（`sat2-prowler`）を削除する
- メンバーロールの StackSet のインスタンスと StackSet 自体を削除する
- 結果の S3 バケットは自動で消えないので、必要な結果を保管したうえで中身を空にして削除する

読み取り専用とはいえ、全アカウントを読めるロールを残しておくのはリスクです。

## 運用のしかた: 四半期ごとの「健康診断」

| タイミング | やること |
|---|---|
| 初回（Lv0 → Lv1） | Basic または Intermediate で全アカウントを診断し、穴の全体像を経営に報告する |
| 改善後 | 同じ条件でもう一度診断し、件数の減り方で効果を示す |
| 四半期ごと（Lv2 まで） | 定期的に診断し、5 章のチェックシートの裏づけにする |
| Lv2 以降 | 常時の点検は Security Hub（FSBP 標準）や Wiz に移し、SATv2 は「別の目」による定期点検として残すか、役目を終える |

SATv2 の結果を **件数の推移** として記録しておくと、「どれだけ良くなったか」を数字で説明できます。セキュリティへの投資を続けてもらうには、この「良くなったことの見える化」が欠かせません。

## SATv2 だけでは分からないこと

- **アプリケーションの脆弱性**: SATv2 は AWS の設定を見るもので、自社のコードの脆弱性は分かりません（10 章）
- **攻撃経路のつながり**: 「公開されている EC2 に、強い権限のロールがついていて、脆弱なパッケージが入っている」といった複数の問題の組み合わせは、個別のチェック結果からは読み取りにくいです（8 章の Wiz、Security Hub の露出検出が得意な領域）
- **AWS 以外**: GitHub、SaaS、社員の PC などは対象外です
