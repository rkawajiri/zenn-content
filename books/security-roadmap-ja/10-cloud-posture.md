**最近のニュースから**

**警察庁（2026 年 9 月）** によると、2026 年上半期のランサムウェア被害の報告は 123 件で、半期で過去最多でした。被害企業の約 6 割が中小企業です。脆弱性を探すなどの不審なアクセスも、前年同期比で約 5 割増えています。自社の環境も、攻撃者から常に外から調べられていると考えておくべきです。

**アサヒグループ（2025 年 9 月）** の調査結果によると、攻撃者はシステム障害が起きる約 10 日前にグループのネットワークに侵入し、主要なデータセンターにアクセスしていました。侵入から被害までには時間があります。その間に「どこから入られると、どこまで到達されるか」という **攻撃経路** を把握し、危ない経路から先にふさいでおけば、被害を防げる可能性が高まります。
:::

9 章で AWS の土台と検知を整えたら、次は「土台がどこまで守れているか」を確かめ、見つかった問題に優先順位をつける段階です。この章では、6 章の役割分担のうち、次の 2 つを扱います。

| 役割 | この本の例 | 費用 | 入れる時期の目安 |
|---|---|---|---|
| AWS 全体の定期点検 | SATv2 | ほぼ無料（無料利用枠に収まるよう設計） | Lv1 から |
| クラウドのリスクの優先順位づけ | Wiz（CNAPP） | 有料 | Lv2〜Lv3。最初は Security Hub の「露出」の検出で代用できる |

## 前半: AWS 全体を定期的に健康診断する ― SATv2

AWS アカウントがたくさんあり、それぞれ違う人が作ってきた会社では、「どこにどんな穴があるのか」を把握するだけで大変です。前半では、AWS が無償で公開している **SATv2** を、一度きりの診断ではなく定期的な健康診断として使う方法を扱います。

### SATv2 とは

**SATv2（Self-Service Security Assessment Solution v2）** は、AWS Labs が GitHub で公開しているソリューションです（[awslabs/aws-security-assessment-solution](https://github.com/awslabs/aws-security-assessment-solution)）。オープンソースのセキュリティ診断ツール Prowler を自社の AWS アカウントの中で動かし、1 つのアカウント、または AWS Organizations 配下の全アカウントを一度に診断します。

| 項目 | 内容 |
|---|---|
| 位置づけ |ある時点の評価（ポイントインタイム評価）。常時監視の道具ではない |
| 仕組み | CloudFormation で CodeBuild などを作り、各アカウントに配った読み取り専用のロールで Prowler が診断する |
| 所要時間 | デプロイ・診断とも数分〜（リソース数と診断の種類による） |
| 費用 | 無料利用枠に収まるよう設計。超えても 1 回あたり 1 ドル未満の見込み（README より） |
| 出力 | アカウントごとの HTML レポート、CSV、JSON / OCSF。オプションで Athena による全社集計とダッシュボード |

診断の種類は 3 つあります。

| 種類 | 内容 | 使いどころ |
|---|---|---|
| Basic | ルートの MFA、公開 S3、開いたセキュリティグループなど、基本的なチェックだけ | 経営への説明用、最初の 1 回 |
|Intermediate（既定） | 重大度 Critical / High のチェックすべて | 定期点検の基本 |
| Full | 650 以上のチェックすべて | Lv2 以降の詳しい点検 |

AWS の「Security Health Improvement Program（SHIP）」というワークショップでも、最初のステップとして SATv2 による評価が使われています。デプロイの手順やパラメーターは README にまとまっているので、ここでは **結果をどう読み、どう使うか** に集中します。

### Security Hub や Wiz があるのに、なぜ SATv2 なのか

常時の点検は、Security Hub（FSBP 標準）や Wiz の役割です（6 章の役割分担）。それでも SATv2 を定期的に使う理由は 3 つあります。

1. **別の目で確かめる**: 同じツールだけを見ていると、そのツールが見ていない穴に気づけません。Prowler は独立したチェックの集まりなので、抜けの確認になります。
2. **全アカウントが本当に対象か確かめる**: Security Hub や Wiz の連携から漏れているアカウントがあっても、SATv2 で Organizations 全体を診断すると見つかります。
3. **改善の推移を、同じ条件で記録する**: 同じ条件で四半期ごとに診断すると、件数の推移がそのまま「どれだけ良くなったか」の証拠になります。経営への報告や、ISMS・SCS 評価制度の証跡にも使えます。

### 結果の読み方

結果は数百〜数千件になることが多いです。全部を一度に見ようとせず、次の順番で絞ります。

1. **Critical / High で、インターネットから到達できるもの**（公開 S3、0.0.0.0/0 のセキュリティグループ、公開スナップショットなど）
2. **ID まわり**（ルートの MFA・アクセスキー、古いアクセスキー、管理者権限を持つ IAM ユーザー）
3. **検知とログ**（CloudTrail・GuardDuty・Config が無効なアカウントやリージョン）
4. それ以外の Critical / High
5. Medium 以下は、Wiz / Security Hub の通常の運用に任せる

#### アカウント別に並べる

もう 1 つの有効な見方は、**アカウントごとの件数** です。件数の多いアカウントは、たいてい次のどれかです。

- 昔の検証用で、持ち主がいない（→ 削除するか、持ち主を決める）
- Control Tower や SCP の管理から外れている（→ 管理下に入れる）
- 特定のチームが急いで作った（→ そのチームと一緒に直し、標準構成を共有する）

**持ち主のいないアカウント** は、削除するか持ち主を決めるかを経営判断にかけます。これだけで件数が大きく減ることがよくあります。

#### Wiz / Security Hub の結果と照らし合わせる

SATv2 で見つかったのに Wiz や Security Hub で出ていない問題があれば、次のどれかです。

- そのアカウントが連携から漏れている（→ 連携を直す。これが一番重要）
- Wiz / Security Hub 側で抑制（suppress）している（→ 抑制の理由が記録されているか確かめる）
- チェックの観点が違う（→ 必要なら Wiz / Security Hub 側にルールを追加する）

### 四半期ごとの運用

| タイミング | やること |
|---|---|
| 四半期の初め | 同じ診断の種類（Intermediate など）・同じ範囲で SATv2 を実行する |
| 実行直後 | 前回との差分を見る。新しく増えたものと、直ったものに分ける |
| 週次レビュー | 新しく増えた Critical / High を、持ち主のチームに割り振る |
| 四半期の終わり | 件数の推移を、4 章のチェックシートと一緒に経営に報告する |

#### 推移を記録する表

| 四半期 | 対象アカウント数 | Critical | High | 持ち主のいないアカウント | 主な改善 |
|---|---|---|---|---|---|
| 2026 Q4 | | | | | |
| 2027 Q1 | | | | | |
| 2027 Q2 | | | | | |

### 注意すること

:::message alert
**結果は機密情報です。** レポートは「自社のどこに穴があるか」の一覧なので、攻撃者にとって最も価値のある情報の 1 つです。共有範囲を絞り、S3 の署名付き URL で共有するときは、URL に作成者の権限が乗ることと有効期限に注意してください。
:::

- **使い終わったら片付ける**: SATv2 は「使ったら消す」前提のソリューションです。読み取り専用とはいえ、全アカウントを読めるロールを残しておくのはリスクです。定期的に使う場合も、実行のたびにデプロイし、終わったらスタックと StackSet を削除する運用にすると安全です。結果の S3 バケットは自動では消えないので、保管するものを決めて管理します。
- **シークレットの検出は既定で対象外**: Lambda のコードや EC2 のユーザーデータなど、中身を読んでシークレットを探すチェックは既定でスキップされます。シークレットの検出は GitHub のシークレットスキャン（11 章）などで補います。
- **AWS の設定以外は見えない**: アプリケーションの脆弱性（12 章）、GitHub、SaaS、社員の PC は対象外です。

## 後半: クラウドのリスクに優先順位をつける ― CNAPP（Wiz）

Security Hub、Inspector、GitHub、AI 診断と道具が増えると、次にぶつかる壁は **「検知結果が多すぎて、どれから直せばいいか分からない」** です。後半では、CNAPP の代表として Wiz を例に、クラウドのリスクの優先順位づけの中心（司令塔）をどう作り、どう使いこなすかを扱います。

:::message
**CNAPP がまだない場合**: 最初から有料の CNAPP を入れる必要はありません。AWS だけを使っているなら、Security Hub の「露出（Exposure）」の検出（9 章）で、攻撃につながる組み合わせをある程度見つけられます。週次レビューと持ち主への割り振りが回り始め、「件数が多すぎて優先順位がつけられない」「マルチクラウドやコードまでたどりたい」と感じた時点が、CNAPP を検討するタイミングです（6 章）。下の「段階的な使い方」は、Security Hub で始める場合にも、そのまま当てはまります。
:::

### Wiz とは

Wiz は、クラウド環境全体のリスクを可視化する **CNAPP**（クラウドネイティブアプリケーション保護プラットフォーム）の代表的な製品です。2026 年 3 月に Google による買収が完了して Google Cloud の一部になりましたが、ブランドは維持され、AWS・Azure・Google Cloud などのマルチクラウドに引き続き対応しています。

#### セキュリティグラフと「有害な組み合わせ」

Wiz の中心にあるのは **Security Graph** です。クラウドのリソース、ID と権限、ネットワークの到達性、脆弱性、シークレット、データの機密度などを 1 つのグラフとしてつなぎ、

> インターネットから到達できる EC2 に重大な脆弱性があり、そのインスタンスには機密データの入った S3 を読める IAM ロールがついている

のような、**個々には中程度でも、組み合わさると危険な状態**（Toxic Combination / 攻撃経路）を見つけます。これによって、数千件の検知結果から本当に危ない数件を選べます。

#### 主なプロダクトとエージェント

| 名前 | 役割 |
|---|---|
|Wiz Cloud| CSPM・脆弱性管理・CIEM（権限の分析）・DSPM（データの把握）・AI-SPM（AI 資産の把握）など |
|Wiz Code| コード・IaC・コンテナイメージをスキャンし、クラウドで見つかったリスクを原因となったコードまでたどる。Claude Code や Cursor などの AI 開発環境向けのスキルもある |
|Wiz Defend| 実行時の脅威の検知と調査 |
|Red Agent| AI の攻撃者として、Web アプリケーションや API のロジックの脆弱性を探し、悪用できるかを確かめる |
|Blue Agent| クラウドのテレメトリ、実行時のシグナル、ID の情報から証拠を集め、検知した脅威の深刻度を調べる |
|Green Agent| 重大な問題を調べ、根本原因（コード、IaC、コンテナイメージ）と担当者を特定し、修正の方法を示す |

（エージェントは 2026 年 3 月に発表されたもので、Red Agent と Blue Agent（Wiz Defend の利用者向け）は一般提供、Green Agent は発表時点でパブリックプレビューでした。提供状況は変わるので、契約内容とあわせて確認してください。）

### Security Hub との分担

6 章で決めたとおり、この本では次のように分担します。

| | Wiz | Security Hub（+ GuardDuty） |
|---|---|---|
| 正とするもの |クラウドのリスクの優先順位と、開発チームへの割り振り|AWS の脅威検知（GuardDuty）と、AWS の中での自動修復|
| 主に見る人 | 推進リーダー（セキュリティの実務の中心になる人。5 章）、各開発チーム | 推進リーダー、インフラ担当 |
| 週次レビューで見るもの | 新しい Critical の攻撃経路（Issues） | GuardDuty の重大度「高」の検知 |
| 得意なこと | 攻撃経路、コードまでのトレース、マルチクラウド | AWS のサービスとの深い統合、EventBridge による自動化 |

Wiz は GuardDuty の脅威検知や、AWS の中での自動修復を置き換えるものではありません。「どれから直すか」は Wiz、「いま攻撃されていないか」は GuardDuty、と役割で分けます。

### 段階的な使い方

Wiz（または同じ役割の道具）が「入れただけ」になっていないかを、次の 4 段階で確かめます。

#### 段階 1: 全体を入れる（Lv1〜Lv2）

- すべての AWS アカウント（新しいアカウントも自動で）が連携されている。前半の SATv2 の結果と照らし合わせて漏れを確かめる
- コンテナレジストリ、Kubernetes、サーバーレスなど、使っている実行環境がすべて対象になっている
- SSO で社内の ID と連携し、権限（誰がどのプロジェクトを見られるか）を管理している

#### 段階 2: 見る数を絞る（Lv2）

最初は Critical だけでも件数が多すぎます。週次レビューでは、次の条件に絞って見ます。

1. **インターネットに露出している**
2. **機密データ、または強い権限につながる**
3. **悪用が確認されている脆弱性**（CISA KEV に載っているなど）を含む

この条件を満たすものだけを「今週直すもの」にし、それ以外は担当チームの通常の対応に任せます。受け入れる（直さない）と決めたものは、理由と期限をつけて抑制します。

#### 段階 3: 持ち主に届ける（Lv3）

推進リーダーが全部を処理するのではなく、リスクの持ち主（開発チーム）に直接届けるようにします。

- **プロジェクト**（Wiz 上の単位）を、AWS アカウント・リポジトリ・チームと対応づける
- 各チームが自分のプロジェクトのリスクだけを見られるようにする
- 重大な問題は Jira などのチケットや Slack に自動で起票し、5 章の SLA で期限をつける
- チームごとの SLA 達成率を、四半期の報告に入れる

#### 段階 4: コードで直す（Lv3〜Lv4）

本番環境を手で直すと、次のデプロイで元に戻ったり、別の環境で同じ問題が起きたりします。**原因となったコード（IaC やコンテナイメージ）を直す** のが根本的な対策です。

- **Wiz Code** で、クラウドの問題がどのリポジトリのどの IaC から来たかをたどる
- **Green Agent** で、根本原因の調査と修正案づくりまで自動化する
- **Red Agent** で、直す前に「本当に悪用できるか」を確かめ、優先順位の精度を上げる
- AI 開発環境向けのスキルを使い、開発者が Claude Code の中から Wiz の検出結果を参照して直せるようにする

### AI 資産の把握

AI-SPM の機能で、クラウド上の AI サービス（Bedrock、SageMaker など）、モデル、AI エージェントの使われ方を把握し、AI 固有の設定ミス（公開されたエンドポイント、過剰な権限など）を見つけます。AWS では Security Hub の AI インベントリでも把握できるので、ここでも「一覧と優先順位は Wiz」と決めておくと二重管理を避けられます（13 章）。

### よくある落とし穴

- **ダッシュボードを眺めて終わる**: Wiz は「見える化」の道具です。見えた問題を誰がいつまでに直すかを決めないと、リスクは減りません。
- **Critical をすべて直そうとする**: 件数が多すぎて止まります。段階 2 の条件で絞ります。
- **推進リーダーが全部を処理する**: 一人目の担当者が全部を抱えると、すぐに回らなくなります。段階 3 の「持ち主に届ける」が、少人数で回すための前提です。
- **費用に見合う使い方になっていない**: 契約の更新前に、「Wiz でなければ見つからなかった攻撃経路」「優先順位づけで減った作業量」「チームごとの SLA 達成率」を数字でまとめておくと、継続の判断と説明がしやすくなります。
