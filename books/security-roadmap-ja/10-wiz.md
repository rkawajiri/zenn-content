**最近のニュースから**

**アサヒグループ（2025 年 9 月）** の調査結果によると、攻撃者はシステム障害が起きる約 10 日前にグループのネットワークに侵入し、主要なデータセンターにアクセスしていました。

侵入から被害までには時間があります。その間に「どこから入られると、どこまで到達されるか」という **攻撃経路** を把握し、危ない経路から先にふさいでおくことが、被害を防ぐ鍵になります。この章では、Wiz を使って攻撃経路で優先順位をつける方法を扱います。
:::

Security Hub、Inspector、GitHub、AI 診断と道具が増えると、次にぶつかる壁は **「検知結果が多すぎて、どれから直せばいいか分からない」** です。この章では、CNAPP の代表として Wiz を例に、クラウドのリスクの優先順位づけの中心（司令塔）をどう作り、どう使いこなすかを扱います。

:::message
**CNAPP がまだない場合**: 最初から有料の CNAPP を入れる必要はありません。AWS だけを使っているなら、Security Hub の「露出（Exposure）」の検出（8 章）で、攻撃につながる組み合わせをある程度見つけられます。週次レビューと持ち主への割り振りが回り始め、「件数が多すぎて優先順位がつけられない」「マルチクラウドやコードまでたどりたい」と感じた時点が、CNAPP を検討するタイミングです（6 章）。この章の「使いこなしの 4 段階」は、Security Hub で始める場合にも、そのまま当てはまります。
:::

## Wiz とは

Wiz は、クラウド環境全体のリスクを可視化する **CNAPP**（クラウドネイティブアプリケーション保護プラットフォーム）の代表的な製品です。2026 年 3 月に Google による買収が完了して Google Cloud の一部になりましたが、ブランドは維持され、AWS・Azure・Google Cloud などのマルチクラウドに引き続き対応しています。

### セキュリティグラフと「有害な組み合わせ」

Wiz の中心にあるのは **Security Graph** です。クラウドのリソース、ID と権限、ネットワークの到達性、脆弱性、シークレット、データの機密度などを 1 つのグラフとしてつなぎ、

> インターネットから到達できる EC2 に重大な脆弱性があり、そのインスタンスには機密データの入った S3 を読める IAM ロールがついている

のような、**個々には中程度でも、組み合わさると危険な状態**（Toxic Combination / 攻撃経路）を見つけます。これが、数千件の検知結果から「本当に危ない数件」を選ぶための鍵になります。

### 主なプロダクトとエージェント

| 名前 | 役割 |
|---|---|
|Wiz Cloud| CSPM・脆弱性管理・CIEM（権限の分析）・DSPM（データの把握）・AI-SPM（AI 資産の把握）など |
|Wiz Code| コード・IaC・コンテナイメージをスキャンし、クラウドで見つかったリスクを原因となったコードまでたどる。Claude Code や Cursor などの AI 開発環境向けのスキルもある |
|Wiz Defend| 実行時の脅威の検知と調査 |
|Red Agent| AI の攻撃者として、Web アプリケーションや API のロジックの脆弱性を探し、悪用できるかを確かめる |
|Blue Agent| クラウドのテレメトリ、実行時のシグナル、ID の情報から証拠を集め、検知した脅威の深刻度を調べる |
|Green Agent| 重大な問題を調べ、根本原因（コード、IaC、コンテナイメージ）と担当者を特定し、修正の方法を示す |

（エージェントは 2026 年 3 月に発表されたもので、Red Agent と Blue Agent（Wiz Defend の利用者向け）は一般提供、Green Agent は発表時点でパブリックプレビューでした。提供状況は変わるので、契約内容とあわせて確認してください。）

## Security Hub との分担

6 章で決めたとおり、この本では次のように分担します。

| | Wiz | Security Hub（+ GuardDuty） |
|---|---|---|
| 正とするもの |クラウドのリスクの優先順位と、開発チームへの割り振り|AWS の脅威検知（GuardDuty）と、AWS の中での自動修復|
| 主に見る人 | 推進リーダー（セキュリティの実務の中心になる人。5 章）、各開発チーム | 推進リーダー、インフラ担当 |
| 週次レビューで見るもの | 新しい Critical の攻撃経路（Issues） | GuardDuty の重大度「高」の検知 |
| 得意なこと | 攻撃経路、コードまでのトレース、マルチクラウド | AWS のサービスとの深い統合、EventBridge による自動化 |

:::message
**Security Hub をやめない**: Wiz は GuardDuty の脅威検知や、AWS の中での自動修復を置き換えるものではありません。「どれから直すか」は Wiz、「いま攻撃されていないか」は GuardDuty、と役割で分けます。
:::

## 使いこなしの 4 段階

Wiz（または同じ役割の道具）が「入れただけ」になっていないかを、次の 4 段階で確かめます。

### 段階 1: 全体を入れる（Lv1〜Lv2）

- すべての AWS アカウント（新しいアカウントも自動で）が連携されている。9 章の SATv2 の結果と照らし合わせて漏れを確かめる
- コンテナレジストリ、Kubernetes、サーバーレスなど、使っている実行環境がすべて対象になっている
- SSO で社内の ID と連携し、権限（誰がどのプロジェクトを見られるか）を管理している

### 段階 2: 見る数を絞る（Lv2）

最初は Critical だけでも件数が多すぎます。週次レビューでは、次の条件に絞って見ます。

1. **インターネットに露出している**
2. **機密データ、または強い権限につながる**
3. **悪用が確認されている脆弱性**（CISA KEV に載っているなど）を含む

この条件を満たすものだけを「今週直すもの」にし、それ以外は担当チームの通常の対応に任せます。受け入れる（直さない）と決めたものは、理由と期限をつけて抑制します。

### 段階 3: 持ち主に届ける（Lv3）

Wiz の価値が最も出るのは、推進リーダーが全部を処理するのではなく、**リスクの持ち主（開発チーム）に直接届ける** ときです。

- **プロジェクト**（Wiz 上の単位）を、AWS アカウント・リポジトリ・チームと対応づける
- 各チームが自分のプロジェクトのリスクだけを見られるようにする
- 重大な問題は Jira などのチケットや Slack に自動で起票し、5 章の SLA で期限をつける
- チームごとの SLA 達成率を、四半期の報告に入れる

### 段階 4: コードで直す（Lv3〜Lv4）

本番環境を手で直すと、次のデプロイで元に戻ったり、別の環境で同じ問題が起きたりします。**原因となったコード（IaC やコンテナイメージ）を直す** のが根本的な対策です。

- **Wiz Code** で、クラウドの問題がどのリポジトリのどの IaC から来たかをたどる
- **Green Agent** で、根本原因の調査と修正案づくりまで自動化する
- **Red Agent** で、直す前に「本当に悪用できるか」を確かめ、優先順位の精度を上げる
- AI 開発環境向けのスキルを使い、開発者が Claude Code の中から Wiz の検出結果を参照して直せるようにする

## AI 資産の把握

AI-SPM の機能で、クラウド上の AI サービス（Bedrock、SageMaker など）、モデル、AI エージェントの使われ方を把握し、AI 固有の設定ミス（公開されたエンドポイント、過剰な権限など）を見つけます。AWS では Security Hub の AI インベントリでも把握できるので、ここでも「一覧と優先順位は Wiz」と決めておくと二重管理を避けられます（13 章）。

## よくある落とし穴

- **ダッシュボードを眺めて終わる**: Wiz は「見える化」の道具です。見えた問題を誰がいつまでに直すかを決めないと、リスクは減りません。
- **Critical をすべて直そうとする**: 件数が多すぎて止まります。段階 2 の条件で絞ります。
- **推進リーダーが全部を処理する**: 一人目の担当者が全部を抱えると、すぐに回らなくなります。段階 3 の「持ち主に届ける」が、少人数で回すための前提です。
- **費用に見合う使い方になっていない**: 契約の更新前に、「Wiz でなければ見つからなかった攻撃経路」「優先順位づけで減った作業量」「チームごとの SLA 達成率」を数字でまとめておくと、継続の判断と説明がしやすくなります。
