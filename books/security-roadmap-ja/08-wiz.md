title: "Wiz によるクラウド横断のリスク管理"
---

Lv2 に上がって Security Hub や Inspector を全アカウントで動かすと、次にぶつかる壁は **「検知結果が多すぎて、どれから直せばいいか分からない」** です。この章では、その壁を越えるための道具として Wiz を位置づけます。

## Wiz とは

Wiz は、クラウド環境全体のリスクを可視化する **CNAPP**（クラウドネイティブアプリケーション保護プラットフォーム）の代表的な製品です。2026 年 3 月に Google による買収が完了し、Google Cloud の一部になりましたが、ブランドは維持され、AWS・Azure・Google Cloud などのマルチクラウドに引き続き対応しています。

### 特徴: セキュリティグラフと「有害な組み合わせ」

Wiz の中心にあるのは **Security Graph** です。クラウドのリソース、ID と権限、ネットワークの到達性、脆弱性、シークレット、データの機密度などを 1 つのグラフとしてつなぎ、

> インターネットから到達できる EC2 に、重大な脆弱性があり、そのインスタンスには機密データの入った S3 を読める IAM ロールがついている

のような、**個々には中程度でも、組み合わさると危険な状態**（Toxic Combination / 攻撃経路）を見つけます。エージェントを入れずに API とスナップショットのスキャンで動くため（エージェントレス）、導入が早いのも特徴です。

### 主なプロダクト

| 名前 | 役割 |
|---|---|
| **Wiz Cloud** | CSPM・脆弱性管理・CIEM（権限の分析）・DSPM（データの把握）・AI-SPM（AI 資産の把握）などをまとめたもの |
| **Wiz Code** | コード・IaC・コンテナイメージをスキャンし、クラウドで見つかったリスクを **原因となったコードまでたどる**。Claude Code や Cursor などの AI 開発環境向けのスキルも提供 |
| **Wiz Defend** | 実行時の脅威検知と対応（クラウドの検知と調査） |

2026 年には、AI エージェントの機能も加わりました。

| エージェント | 役割 |
|---|---|
| **Red Agent** | 攻撃者の振る舞いをまねて、攻撃経路が本当に悪用できるかを検証する |
| **Blue Agent** | 検知した脅威の調査とトリアージを支援する |
| **Green Agent** | リスクの根本原因（コード、IaC、コンテナイメージ）と担当者を特定し、修正コードや PR を提案する |

（提供状況は機能ごとに一般提供 / プレビューが分かれており、変化が速いため、導入時に確認してください。）

## Security Hub と Wiz の使い分け

どちらも「クラウドの検知結果を集めて優先順位をつける」道具なので、役割が重なります。専任チームのない会社では、**最初から両方を本格運用するのは負担が大きい** です。

| 観点 | AWS Security Hub（+ GuardDuty / Inspector） | Wiz |
|---|---|---|
| 費用 | 比較的安い。使った分だけ | ライセンス費用が大きい（ワークロード数などで決まる） |
| 導入 | AWS の中で完結。Organizations と統合 | 外部 SaaS。読み取りロールを渡すだけで早い |
| 強み | AWS のサービスとの深い統合、自動修復との連携、脅威検知（GuardDuty） | 攻撃経路の可視化、優先順位づけの精度、コードまでのトレース、マルチクラウド |
| 弱み | 攻撃経路の文脈は改善中だが Wiz ほどではない。AWS 以外は限定的 | 費用。AWS 内の検知（GuardDuty）を置き換えるものではない |

### おすすめの進め方

1. **Lv1〜Lv2 は AWS 標準で固める**: GuardDuty、Security Hub、Inspector を全アカウントに展開し、「毎週誰かが見る」運用を作る。まずここで、検知結果を処理する筋肉をつける
2. **Lv2 → Lv3 の壁で Wiz を検討する**: 次のどれかに当てはまったら、Wiz（または同種の CNAPP）の導入を検討する
   - 検知結果が多すぎて、毎週のレビューで処理しきれない
   - AWS 以外のクラウド（Azure / Google Cloud）も本格的に使っている
   - アカウント数が多く、各開発チームに「自分のチームのリスク」を見せたい
   - 取引先や監査で、クラウドのリスク管理の成熟度を示す必要がある
3. **導入したら役割を決める**: 「優先順位づけと開発チームへの割り振りは Wiz」「脅威検知とインシデント対応の起点は GuardDuty」のように、どちらで何を見るかを決めて二重運用を避ける

:::message
**PoC（試験導入）のすすめ**: Wiz は読み取りロールを渡すだけで数時間で結果が出るので、契約前に PoC をするのが一般的です。PoC では、7 章の SATv2 や Security Hub の結果と比べて、「Wiz でなければ見つからなかった攻撃経路があるか」「優先順位づけで処理件数がどれだけ減るか」を評価基準にすると、費用対効果を判断しやすくなります。
:::

## Wiz を入れた後の運用（Lv3）

### 開発チームに直接届ける

Wiz の価値が最も出るのは、セキュリティ担当者が全部を処理するのではなく、**リスクの持ち主（開発チーム）に直接届ける** ときです。

- プロジェクト（Wiz 上の単位）を AWS アカウントやリポジトリと対応づけ、各チームが自分のリスクだけを見られるようにする
- 重大な問題（Critical の攻撃経路など）は、Jira などのチケットや Slack に自動で起票する
- 対応期限（SLA）をチームごとに測る

### コードまでたどって直す

Wiz Code を使うと、クラウドで見つかった問題（例: 公開された S3）が、**どのリポジトリのどの IaC で作られたか** までたどれます。本番環境を手で直すのではなく、IaC を直して PR にすることで、同じ問題の再発を防げます。Green Agent のような AI エージェントを使えば、修正 PR の下書きまで自動化できます。

### AI 資産の把握

AI-SPM の機能で、クラウド上の AI サービス（Bedrock、SageMaker など）、モデル、AI エージェントの利用状況を把握し、AI 固有の設定ミス（公開されたエンドポイント、過剰な権限など）を見つけます。AWS だけなら Security Hub の AI インベントリでも把握できます（6 章・11 章）。

## よくある落とし穴

- **入れただけで満足する**: Wiz は「見える化」の道具です。見えた問題を誰がいつまでに直すかを決めないと、リスクは減りません。
- **Critical をすべて直そうとする**: 最初は数が多すぎます。「インターネットから到達でき、かつ機密データや強い権限につながるもの」から順に、件数を絞って取り組みます。
- **Security Hub をやめてしまう**: Wiz は GuardDuty の脅威検知や、AWS の自動修復の仕組みを置き換えるものではありません。役割を分けて併用します。
