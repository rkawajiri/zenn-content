---
title: "現在地チェックシート"
---

この章は、自社の現在地を測るためのチェックシートです。**四半期に一度**、この章をコピーして埋め、前回との差分を経営に報告することを想定しています。

## 使い方

1. 7 つの領域ごとに、各レベルの項目にチェックを入れる
2. **その領域のレベル ＝ そのレベルと、それより下のすべてのレベルの項目にチェックが入った、一番高いレベル**（Lv2 の項目がすべて埋まっていても、Lv1 に 1 つ空きがあれば Lv1 未満、つまり Lv0）
3. **会社全体のレベル ＝ 一番低い領域のレベル**（3 章の原則 3）
4. チェックが入らなかった項目のうち、一番低いレベルのものが「次の一手」の候補になる
5. 領域ごとに、**次のレベルの項目の達成率**（例: Lv2 の 8 項目のうち 5 項目で 63%）も記録する。レベルは 1 項目欠けるだけで上がらないので、四半期ごとの前進は達成率のほうに表れる

このチェックシートは、この本のレベルで「いまどこにいて、次に何をするか」を測るための **物差し** です。項目は、各レベルの中核になるものに絞っています。SCS 評価制度 ★3 の要求事項と評価基準をすべて並べたものではないので、★3 を目指す場合は、Lv2 の項目がそろってきた段階で、19 章の「★3 準備チェック表」で最終確認してください。

:::message
**判定は厳しめに。** 「だいたいできている」は「できていない」として数えます。「一部のアカウントだけ」「やったことはあるが続いていない」も未達です。甘く判定すると、本当の穴が見えなくなります。
:::

## A. 組織・ガバナンス

**Lv1**
- [ ] セキュリティの窓口（担当者）が社内外に明示されている
- [ ] IPA の「5 分でできる！情報セキュリティ自社診断」をやったことがある

**Lv2**
- [ ] セキュリティ責任者（CISO 相当）が経営層または経営直下に任命されている
- [ ] 兼務チームのメンバー・役割・稼働（例: 各人 10〜20%）が明文化されている
- [ ] セキュリティ基本方針と、守秘義務・情報の機密区分のルールを経営が承認し、社員に周知している
- [ ] 情報資産（PC・サーバ・ネットワーク機器・SaaS・AWS アカウント・重要な機密情報）の一覧がある
- [ ] リスク登録簿があり、受容したリスクも記録されている
- [ ] 委託先・SaaS について、導入時の確認手順と、機密情報の取扱い・インシデント時の役割分担の取り決めがある
- [ ] 取引先から ★3 を求められている（または求められそうな）場合、19 章の準備チェック表で自己評価した

**Lv3**
- [ ] 経営ガイドラインの重要 10 項目に沿った定期報告（四半期）をしている
- [ ] 主要な規程（アクセス管理、委託先管理、インシデント対応、AI 利用など）が揃い、年 1 回見直している
- [ ] 委託先・SaaS を年 1 回見直している
- [ ] 全社員向けの教育（年 1 回以上）と、標的型メール訓練をしている
- [ ] SCS 評価制度 ★4 の要求事項に対するギャップを把握している

**Lv4**
- [ ] セキュリティ指標を経営が定期的に確認し、予算配分に使っている
- [ ] 各部門にセキュリティチャンピオンがいる
- [ ] 専任者（または専任者と外部パートナー）が、自社の規模に合った形でいる
- [ ] 取引先・顧客に向けてセキュリティの取り組みを開示している

## B. ID と社内 IT（7・8 章）

**Lv1**
- [ ] 全 AWS アカウントのルートユーザーに MFA があり、アクセスキーがない
- [ ] メール・グループウェア、GitHub、AWS、主要 SaaS で MFA が必須
- [ ] 退職者のアカウントが削除されていることを一度点検した
- [ ] 社員の PC で OS の自動更新とウイルス対策が有効
- [ ] VPN 機器・ファイアウォールの一覧があり、最新の状態になっている
- [ ] 振込先の変更などを、メール以外の手段で確認する手順がある

**Lv2**
- [ ] 社員の ID が 1 つの IdP（Entra ID / Google Workspace / Okta など）に集約され、主要サービスに SSO でログインしている
- [ ] ID と権限の付与・変更・削除が申請・承認制で、定期的（半年に 1 回など）に棚卸しをして、使われていない ID や不要な権限を削除している
- [ ] 管理者権限を持つ人の一覧があり、管理用のアカウントを日常のアカウントと分け、権限を最小限にしている
- [ ] パスワードのルールを決めて周知し、SSO できないサービスや共有アカウントのパスワードを、会社のパスワードマネージャーで管理している
- [ ] 会社の PC とスマートフォンを MDM で管理し、ディスクの暗号化、画面ロック、入れてよいソフトの制限をしている
- [ ] インターネットとの境界の機器の重大な更新を 14 日以内に当て、ファイアウォールのルールと管理パスワードを管理している
- [ ] 社内ネットワークの境界（UTM など）か端末（EDR など）で、不正な通信をリアルタイムに検知・遮断し、通知が届く
- [ ] 自社のドメインに SPF・DKIM・DMARC を設定している
- [ ] 業務で使う SaaS の一覧と管理者があり、共有設定を見直した

**Lv3**
- [ ] IAM Access Analyzer などで、未使用の権限・外部からのアクセスを検出して減らしている
- [ ] フィッシング耐性のある MFA（パスキー / FIDO2）を管理者から導入している
- [ ] 本番環境への強い権限は、必要なときだけ申請して使う（一時的な権限付与）
- [ ] すべての PC に EDR があり、止められたら通知が来る
- [ ] DMARC のポリシーが quarantine 以上
- [ ] 社員が同意できる OAuth アプリを管理者が制限している
- [ ] IdP が使えないときの緊急用の管理者アカウント（break-glass）があり、使われたら通知が来る
- [ ] 退職予定者の大量ダウンロードや外部共有に気づける（SaaS の監査ログなど）

**Lv4**
- [ ] 人以外の ID（CI/CD、AI エージェント、ワークロード）も一覧化され、最小権限と短命な認証情報で管理されている
- [ ] デバイスの状態（OS 更新、EDR）を条件にしたアクセス制御をしている
- [ ] VPN に頼らず、ID と端末の状態でアクセスを許す仕組みに移行している

## C. AWS 基盤・インフラ（9 章）

**Lv1**
- [ ] AWS アカウントの一覧があり、それぞれの責任者が分かる
- [ ] 全アカウント・全リージョンで CloudTrail が有効
- [ ] S3 のパブリックアクセスブロックがアカウント単位で有効
- [ ] 意図しない公開（S3、0.0.0.0/0 のセキュリティグループ、公開スナップショットなど）を一度点検し、直した
- [ ] 各アカウントにセキュリティ連絡先（代替連絡先）が登録されている

**Lv2**
- [ ] AWS Organizations / Control Tower で全アカウントを管理している
- [ ] 人の AWS へのアクセスは IAM Identity Center 経由で、IAM ユーザーの長期アクセスキーは原則ない
- [ ] ログアーカイブ用・セキュリティ（監査）用の専用アカウントがあり、SCP で記録の停止や使わないリージョンを禁止している
- [ ] AWS Config が全アカウントで有効で、サーバ（EC2 など）の台数と OS を把握している
- [ ] 本番の設定変更が申請・承認制（変更のチケットや IaC の PR レビュー）で、開発環境の管理者権限では本番を操作できない
- [ ] セキュリティグループのインバウンドのルールを決め、不要になったルールを消している
- [ ] サーバにもマルウェア対策がある（GuardDuty の EC2 向けマルウェア保護、エージェント型の製品など）
- [ ] 重要なデータが暗号化され、バックアップが別アカウント・別リージョンにもある

**Lv3**
- [ ] 新しいアカウントを作ると、標準のガードレールと監視が自動で入る
- [ ] インフラの多くが IaC（Terraform / CloudFormation / CDK）で管理され、PR ごとにセキュリティスキャンが走る
- [ ] 重大な設定ミスの一部（公開 S3 など）が自動修復される
- [ ] バックアップは別アカウントに、削除できない形（ボールトロックなど）で保管され、暗号化キーも本番の管理者が消せない場所にある
- [ ] ログ用バケットにオブジェクトロックがかかっている
- [ ] バックアップの復元テストが定期的に（自動で）行われている

**Lv4**
- [ ] 本番環境への人の手による変更は原則なく、変更はすべてパイプライン経由
- [ ] 定期的に障害・攻撃を想定した復旧訓練（GameDay）をしている

## D. 検知と脆弱性管理（5・9・10・14 章）

**Lv1**
- [ ] 全アカウント・全リージョンで GuardDuty が有効
- [ ] SATv2 などで AWS 全体の健康診断を一度した
- [ ] GuardDuty の重大度「高」の通知が、誰かのチャットに届く

**Lv2**
- [ ] Security Hub（または Wiz）で検知結果を集約し、毎週見る担当者と時間が決まっている
- [ ] 攻撃の兆しの知らせ（GuardDuty、EDR、IdP の危険なサインインなど）が共有のチャンネルに集まり、届いたら確かめてインシデントかどうかの判断を記録している。EDR やログが止められたら通知が来る
- [ ] OS・コンテナ・ライブラリの脆弱性を Amazon Inspector などでスキャンしている
- [ ] OS・ミドルウェア・ネットワーク機器の Critical / High の更新を、リリースから 14 日以内に適用している
- [ ] 外部に公開しているもの（ドメイン、IP、エンドポイント、モバイルアプリが使う API を含む）の一覧がある
- [ ] 注意喚起・脆弱性情報（JPCERT/CC、JVN、CISA KEV など）を受け取る場所が決まっていて、自社が使っているかをすぐに確かめられる

**Lv3**
- [ ] 重大度ごとに対応期限（SLA）があり、達成率を測っている
- [ ] 検知結果が、到達可能性や攻撃経路など「文脈」で優先順位づけされている（Wiz、Security Hub の露出検出など）
- [ ] 検知から担当チームへのチケット起票が自動化されている
- [ ] 誤検知や受容したものが、理由つきで抑制（suppress）されている
- [ ] 夜間・休日の知らせにも一次対応できる（当番、MDR、AWS Security Incident Response など）

**Lv4**
- [ ] AI エージェントがトリアージと修正案の作成を担い、人は承認と例外対応に集中している
- [ ] 外部のペネトレーションテスト（AI によるものを含む）を定期的に行っている

## E. 開発・コード（11・12 章）

**Lv1**
- [ ] GitHub の組織で 2 段階認証が必須
- [ ] シークレットスキャンとプッシュ保護が有効
- [ ] Dependabot アラートが有効

**Lv2**
- [ ] GitHub の組織が IdP と SSO 連携している
- [ ] デフォルトブランチがルールセット / ブランチ保護で守られ、レビュー必須
- [ ] GitHub Actions から AWS へのアクセスは OIDC で、長期キーを使っていない
- [ ] 外部コラボレーターと、組織に入っている GitHub App の一覧がある
- [ ] 公開している API で、利用者ごとの認可チェック（他人のデータを ID の書き換えで取れない）とレート制限をしている（12 章）

**Lv3**
- [ ] PR ごとに SAST（CodeQL など）と依存関係のチェックが走る
- [ ] AI による脆弱性診断（Takumi / Claude Security など）と自動修正の仕組みがある
- [ ] 悪性パッケージの混入を防ぐ仕組み（Takumi Guard など）がある
- [ ] Actions のサードパーティアクションをコミット SHA で固定している
- [ ] リリース前の DAST（動的診断）を定期的に行っている
- [ ] 自社サービスの利用者アカウントを、パスワードリスト攻撃から守っている（ログインの試行制限、MFA やパスキーの提供など。12 章）

**Lv4**
- [ ] 新機能の設計時に脅威モデリングをしている
- [ ] SBOM を生成・管理している
- [ ] 開発者向けのセキュリティ教育と、セキュリティチャンピオン制度がある

## F. AI の利用・開発（13 章）

**Lv1**
- [ ] 業務で使ってよい AI サービスと、入力してはいけない情報が決まっている
- [ ] 会社として契約した AI サービス（学習に使われない設定）が用意されている

**Lv2**
- [ ] AI 利用ルール（ガイドライン）が文書化され、周知されている
- [ ] AI コーディングエージェントの利用ルール（権限、自動承認の範囲、使ってよいリポジトリ）がある
- [ ] 社内で使われている AI サービス・MCP サーバーの一覧がある

**Lv3**
- [ ] AI エージェントの実行環境がサンドボックス化され、使える認証情報が最小限
- [ ] 自社プロダクトの AI 機能について、OWASP Top 10 for LLM / Agentic を使ったリスク評価をしている
- [ ] Security Hub の AI インベントリなどで、AWS 上の AI 資産を把握している
- [ ] AI 機能にガードレール（Bedrock Guardrails など）と、ログの記録がある

**Lv4**
- [ ] AI 機能のレッドチーミング（攻撃テスト）を定期的に行っている
- [ ] AI エージェントの ID・権限・行動ログを、人の ID と同じように管理している

## G. インシデント対応と復旧（15・16 章）

**Lv1**
- [ ] インシデントのときに最初に連絡する人（社内）と、相談先（外部の専門会社、IPA、JPCERT/CC など）が決まっている
- [ ] サイバー保険の有無と内容（調査費用が補償されるか）を把握している
- [ ] 注意喚起が出たときに、直近 1 か月の CloudTrail と IdP のログを確かめたことがある

**Lv2**
- [ ] インシデント対応の手順（発見・報告 → 初動 → 調査・封じ込め → 復旧 → 最終報告）、報告フォーマット、関係当局を含む報告ルートが文書化され、関係者に説明・訓練している
- [ ] 個人情報漏えい時の報告義務（個人情報保護委員会への報告など）を把握している
- [ ] 止まると困る業務ごとに、目標復旧時間と、代わりの手段（予備の環境、電話・ファクスでの受付など）を決めている
- [ ] 重要システムのバックアップについてリストア手順書があり、一度は復旧を試した

**Lv3**
- [ ] AWS アカウント侵害、ランサムウェア、シークレット漏えいなど、主要なシナリオ別の手順（プレイブック）がある
- [ ] 年 1 回以上、机上訓練をしている
- [ ] 調査に必要なログ（CloudTrail、VPC フローログ、アプリのログ）が 1 年以上、別アカウントに改ざんできない形で保管されている
- [ ] 平時の侵害調査（16 章）を年 1 回以上行い、結果を記録している
- [ ] フォレンジックの調査会社の候補が決まっている（保険会社の提携先、AWS Security Incident Response など）

**Lv4**
- [ ] 初動の一部（隔離、キーの無効化など）が自動化されている
- [ ] インシデントのたびに振り返りを行い、再発防止策がロードマップに入る

## 結果の読み方の例

架空の会社で記入した例です。検知のツールはある程度入っている、という想定です。

| 領域 | レベル | 達成率 | 理由 |
|---|---|---|---|
| A. 組織・ガバナンス | Lv1 | 3/7 | 担当者はいるが、責任者の任命と稼働の確保が明文化されていない |
| B. ID と社内 IT | Lv1 | 4/9 | MFA は必須だが、IdP への集約と管理者アカウントの分離ができていない |
| C. AWS 基盤 | Lv1 | 5/8 | Organizations はあるが、Control Tower の管理から外れたアカウントがある |
| D. 検知と脆弱性管理 | Lv1 | 3/6 | 検知のツールは入っているが、毎週見る人と時間が決まっていない |
| E. 開発・コード | Lv2 | 2/6 | GitHub の設定は標準化済み。ただし AI 診断の結果を処理する期限がない |
| F. AI | Lv1 | 1/3 | 利用ルールの最低限はあるが、AI コーディングエージェントの標準設定がない |
| G. インシデント対応 | Lv0 | 2/3 | 連絡先が決まっていない |

達成率は、次のレベル（E は Lv3、G は Lv1、それ以外は Lv2）の項目のうち、チェックが入った数です。

この場合、**全体のレベルは Lv0** です。ツールがそろっていても、G（インシデント対応）の連絡先が決まっていないだけで全体は Lv0 になります。攻撃者は一番弱いところを狙うからです。

次の一手は、

1. まず G を Lv1 に上げる（連絡先と相談先を決める。数日でできる）
2. 次に D を Lv2 に上げる（週次レビューを始める。ツールはもうあるので、時間を確保するだけ）
3. そのあと A・B・C を Lv2 に上げる（17 章のフェーズ 1〜2）

となります。全体のレベルは Lv0 のままでも、四半期ごとに達成率の数字が上がっていけば、前に進んでいることを経営に示せます。この例のように、ツールがそろっていても全体のレベルは低いことがよくあり、「ツールを足す」より「入っているツールを回す」ほうが次の一手になります。ツールがまだ少ない会社では、次の一手は 6 章の「まだ入っていないときの順番」に沿って、無料・標準の機能を全体に入れることから始まります。
