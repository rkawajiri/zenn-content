---
title: "付録: SCS 評価制度 ★3 準備チェック表"
---

この付録は、SCS 評価制度 ★3 を取る準備ができているかを確かめるためのチェック表です。4 章のチェックシートは「この本のレベルで、いまどこにいるか」を測る物差しで、項目を中核のものに絞っています。★3 では、それより細かいこと（周知、記録、年 1 回の点検、パスワードの文字数など）まで問われるので、この表で確かめます。

## 使い方

- 4 章の Lv2 の項目がそろってきた段階で使います。取引先から ★3 を急がれている場合は、17 章の「取引先から ★3 を急がれているとき」のとおり、最初にこの表でギャップを洗い出します
- 表は、★3 の 26 の要求事項ごとに、81 の評価基準を言い換えてまとめたものです。番号（例: 4-1-3）は要求事項の番号です
- **言い換えなので、正式な自己評価には、IPA の「[SCS-620 ★3・★4 要求事項・評価基準 解説書](https://www.ipa.go.jp/security/scs/rcu1hd0000007a2i-att/SCS-620-handbook-v1.0.pdf)」（2026 年 10 月 28 日版）の評価基準を使ってください**。解説書には、評価基準ごとの考え方や、よくある質問への回答も載っています
- 「周知」「記録」「年 1 回の点検」が多く出てきます。仕組みを作るだけでなく、その証跡を残すところまでが ★3 の範囲です。いつ何を点検し、何を記録するかは、5 章の「★3 のための文書と記録」にまとめています
- 要求事項ごとに、やり方が書いてあるこの本の章（「本:」）と、IPA の「[中小企業の情報セキュリティ対策ガイドライン](https://www.ipa.go.jp/security/keihatsu/sme/guideline/)」付録 5「情報セキュリティ関連規程（サンプル）」の該当箇所（「規程サンプル:」）を示しています。規程サンプルは第4.0版で SCS 評価制度に沿って見直され、末尾に規程サンプルと SCS 評価制度の要求事項の対応表が付いています（「組織的対策 6（アクセス制御及び認証）」は、対応表の「1-6」の節です。対応表の番号は SCS の要求事項の番号と形が似ているため、ここでは区分と節の名前で書いています）。規程を書くときは、この対応表を使うと漏れを防げます

---

## 1. ガバナンスの整備（5 章）

**1-2-1 セキュリティ推進活動部門**

本: 5 章（体制）／規程サンプル: 組織的対策 1（情報セキュリティのための組織）

- [ ] セキュリティを統括する役員（CISO 相当）と、担当部署の役割・責任を定めている
- [ ] 平時の体制の連絡先リストがある
- [ ] 体制と連絡先リストを年 1 回点検している

**1-2-3 守秘義務のルール**

本: 5 章（規程、★3 のための文書と記録）／規程サンプル: 人的対策 1〜3（雇用条件、従業員の責務、雇用の終了）

- [ ] 役員・従業員・派遣社員・受入出向者を対象に、守秘義務のルールを定めている
- [ ] 入社時や社外の人を受け入れるときに、守秘義務のルールを説明している

**1-3-1 セキュリティ対応方針の策定**

本: 5 章（規程）／規程サンプル: 組織的対策 4（情報セキュリティ基本方針の制定・管理）

- [ ] セキュリティ対応方針（基本方針）を定めている
- [ ] 全員が最新の方針をいつでも参照できる
- [ ] 方針を改正したときに、全員に周知している

## 2. 取引先管理（5 章）

**2-1-1 取引先とのビジネス又はシステム上の関係**

本: 5 章（委託先・SaaS の管理）／規程サンプル: 組織的対策 5（情報資産・IT資産の管理）、組織的対策 8（委託管理）

- [ ] 取引先やクラウド事業者が管理し、自社の資産が接続しているシステムを把握する仕組みがある
- [ ] その内容を年 1 回点検している

**2-1-2 機密情報の取扱い**

本: 5 章（委託先・SaaS の管理）／規程サンプル: 組織的対策 8（委託管理）

- [ ] 機密情報を共有する取引先・子会社と、業務開始前に、機密情報の定義、利用制限・保管方法・複製や第三者提供の可否、返還・廃棄を取り決めている

**2-1-4 セキュリティインシデント発生時の役割・責任**

本: 5 章（委託先・SaaS の管理）／規程サンプル: 組織的対策 8（委託管理）

- [ ] 機密情報を共有する取引先・子会社と、インシデント発生時の役割と責任を定めている

## 3. リスクの特定（4・6・8・9 章）

**3-1-1 情報機器、OS 及びソフトウェアに関する情報の把握**

本: 8 章（社員の PC）、9 章（AWS）／規程サンプル: 組織的対策 5（情報資産・IT資産の管理）、技術的対策 3（IT基盤運用管理）

- [ ] PC（シンクライアントを含む）の製造元・OS・台数を把握する仕組みがある（MDM など）
- [ ] サーバ・仮想サーバ・ハイパーバイザの製造元・OS・台数を把握する仕組みがある（AWS Config、Inspector のインベントリなど）
- [ ] 機器・OS・ソフトウェアの導入、設置、ネットワーク接続、パッチ適用のルールを定めている
- [ ] そのルールが守られているかを年 1 回点検している

**3-1-2 ネットワークに関する情報の把握**

本: 8 章（VPN・ネットワーク機器）／規程サンプル: 技術的対策 3（IT基盤運用管理）

- [ ] ネットワークを把握する仕組みがあり、各ネットワークの所在地と用途が分かる
- [ ] ネットワーク機器の製造元・モデル・保守事業者を把握する仕組みがある

**3-1-3 外部情報サービスの管理**

本: 5 章、8 章（業務の SaaS）／規程サンプル: 技術的対策 3（IT基盤運用管理）

- [ ] SaaS などの外部情報サービスを使うときのセキュリティ要件を定め、使う前に満たしているかを確かめている
- [ ] 外部情報サービスの提供事業者と、機密情報の取扱いについて合意している（個別の合意が難しいサービスの扱いは解説書を参照）

**3-1-4 機密区分に応じた情報の管理**

本: 5 章（規程）、9 章（データ保護）／規程サンプル: 組織的対策 5（情報資産・IT資産の管理）

- [ ] 機密の特定、機密区分の判定と表示、区分に応じた取扱方法、取扱エリアの区分と制限を含む管理ルールを定めている
- [ ] そのルールを年 1 回点検している
- [ ] 重要な機密情報ごとに、管理者・部署・保管場所・保管期限・開示先・連絡先を把握する仕組みがある

## 4. 攻撃等の防御（5・7・8・9・11・15 章）

**4-1-1 ユーザ ID の管理手続**

本: 7 章（ID）／規程サンプル: 組織的対策 6（アクセス制御及び認証）

- [ ] ユーザ ID の付与・変更・削除が申請・承認制になっている
- [ ] ID を共有していない（やむを得ず共有するなら、誰が使ったかを特定できる）
- [ ] 退職したときや、一定期間使われていないときに、ID を速やかに削除・無効化している
- [ ] 役割が変わったときに、不要になった権限を速やかに削除・無効化している

**4-1-2 管理者 ID の管理手続**

本: 7 章（ID）、9 章（ID とアクセス）／規程サンプル: 組織的対策 6（アクセス制御及び認証）

- [ ] すべてのサーバとネットワーク機器に、システム管理者と責任者を定めている
- [ ] 管理者権限を持つ人を限定し、管理者 ID を共有していない（やむを得ず共有するなら、誰が使ったかを特定できる）
- [ ] 管理者 ID には、用途に応じた最小限の権限だけを与えている
- [ ] 開発環境の管理者権限で、本番環境を操作できないようにしている
- [ ] 誰が管理者 ID を持っているかを把握する仕組みがある
- [ ] 退職したときや、一定期間使われていないときに、管理者 ID を速やかに削除・無効化している
- [ ] 管理者 ID の付与・変更・削除が申請・承認制になっている
- [ ] 管理者 ID の付与・変更・削除と、サーバ・ネットワーク機器の設定変更ができる人を、業務上必要な人に限定している

**4-1-3 認証の強度・実装方法の決定**

本: 7 章（ID）、9 章、11 章／規程サンプル: 組織的対策 6（アクセス制御及び認証）

- [ ] すべての ID で、アクセスの前にパスワードなどで認証している
- [ ] 重要な機密情報を扱うクラウドサービスでは、利用者も管理者も常に多要素認証を使っている
- [ ] 多要素認証は、知識・所有・生体・その他（IP アドレスなど）のうち 2 種類以上を組み合わせている
- [ ] 多要素認証で使うパスワードは 8 文字以上にしている

**4-1-4 アカウントロック制御**

本: 7 章（ID）、8 章（社員の PC）／規程サンプル: 組織的対策 6（アクセス制御及び認証）

- [ ] PC のログオンとスマートデバイスのロック解除で、失敗のたびに試行間隔を長くするか、10 回以上の失敗でロックしている（どちらもできなければ、より強いパスワードなどの代替策）
- [ ] PC のログオンとスマートデバイスのロック解除に、6 文字以上のパスワードか PIN を使っている

**4-1-5 パスワード設定ルール**

本: 7 章（ID）／規程サンプル: 組織的対策 6（アクセス制御及び認証）

- [ ] PC・サーバ・スマートデバイス・クラウドサービスの初期パスワードを変えるルールがある
- [ ] 推測されやすい語を禁止するルールがある
- [ ] 多要素認証か、10 回の失敗でのロックと 8 文字以上のパスワードを組み合わせるルールがある（どちらもできなければ、英大文字・小文字・数字を含む 10 文字以上）
- [ ] 機器やサービスの間でパスワードを使い回さないルールがある
- [ ] これらのルールを全員に周知している

**4-1-6 パスワード管理ルール**

本: 7 章（ID）、11 章（シークレットが漏れたとき）／規程サンプル: 組織的対策 6（アクセス制御及び認証）

- [ ] パスワードを安全に保管するルールがある（パスワード管理アプリの利用など）
- [ ] パスワードが漏れた、または漏れた疑いがあるときに、速やかに変える手順がある
- [ ] これらのルールを全員に周知している

**4-1-7 アクセス権の管理ルール**

本: 7 章（ID）。部屋への入室の管理はこの本では扱っていない／規程サンプル: 組織的対策 6（アクセス制御及び認証）、物理的対策 1（入室権限およびセキュリティ領域）

- [ ] 業務システムと PC のアクセス権、機密上の配慮が必要な部屋への入室について、申請・承認制、必要な範囲への限定、定期的な棚卸し、申請書や台帳の管理を含むルールを定めている

**4-2-2 セキュリティインシデント発生時の教育・訓練**

本: 5 章（教育、★3 のための文書と記録）、15 章（訓練）／規程サンプル: 人的対策 4（情報セキュリティ教育）

- [ ] 新しく人を受け入れたときと年 1 回以上、インシデント発生時の対応について、資料の配布に加えて e ラーニングか集合形式で教育・訓練をしている
- [ ] 教育・訓練の内容・方法・時期・受講状況を記録している
- [ ] 教育・訓練の内容を年 1 回点検している

**4-3-4 適切なバックアップ**

本: 9 章（バックアップを守る）／規程サンプル: 技術的対策 4（バックアップ）

- [ ] 取得対象・頻度・保管期間を決めて、バックアップを取っている
- [ ] 重要な機密情報は、遠隔地にもバックアップしている（別リージョンなど）
- [ ] バックアップの対象ごとに、リストア手順書がある

**4-4-1 情報機器、OS 及びソフトウェアの安全な構成**

本: 8 章（社員の PC）、9 章（変更管理）／規程サンプル: 技術的対策 3（IT基盤運用管理）

- [ ] PC・サーバ・スマートデバイスで、許可していないソフトウェアを削除・無効化しているか、自由にインストールできないようにしている
- [ ] 外部記憶媒体の自動実行・自動再生を無効にしている
- [ ] サーバとネットワーク機器の設定変更が、申請・承認制になっている

**4-4-4 セキュリティパッチ・アップデートの手続**

本: 5 章（脆弱性管理の SLA）、8 章（社員の PC）／規程サンプル: 技術的対策 2（IT機器利用）、技術的対策 3（IT基盤運用管理）

- [ ] 機器・OS・ソフトウェアがライセンスとサポートのあるものになっている（サポートが切れたものは削除するか、インターネットとの通信を遮断する。やむを得ず使うなら、リスクを下げる対策をする。できれば自動更新）
- [ ] Critical / High（CVSS 7.0 以上など）の脆弱性を直す更新を、リリースから 14 日以内に適用している（適用できないときの扱いは解説書を参照）

**4-4-5 マルウェア感染からの保護**

本: 8 章（社員の PC）、9 章（サーバのマルウェア対策）／規程サンプル: 技術的対策 2（IT機器利用）

- [ ] ネットワークにつながるすべての PC とサーバに、マルウェア対策ソフトウェアを入れている
- [ ] PC とサーバごとに、スキャンの範囲と頻度を決めて実行している
- [ ] パターンファイルを、ベンダーの推奨どおりに更新している

**4-5-1 ネットワーク境界防護**（クラウドのセキュリティグループも、ファイアウォールと同等の技術として扱われる。解説書の 3.3.3 を参照）

本: 8 章（VPN・ネットワーク機器）、9 章（ネットワーク）／規程サンプル: 技術的対策 3（IT基盤運用管理）

- [ ] すべてのファイアウォールとルーターの初期の管理パスワードを強固で一意のものに変えたか、リモートからの管理を無効にしている
- [ ] ファイアウォールとルーターのパスワードを変える手順がある
- [ ] ファイアウォールとルーターの認証が、4-1-5 のパスワードのルールを満たしている
- [ ] 認証されていないインバウンドの通信を遮断している
- [ ] インバウンドの通信のファイアウォール・ルールを定めている
- [ ] 不要になったルールを速やかに削除・無効化している
- [ ] ルールをインターネット経由で変えるときは、多要素認証を使うか、接続元の IP アドレスを限定している

## 5. 攻撃等の検知（8・9・14 章）

**5-1-1 ネットワーク接続・データの監視**

本: 8 章（VPN・ネットワーク機器）、9 章（検知）、14 章（見張り）／規程サンプル: 技術的対策 3（IT基盤運用管理）

- [ ] ネットワークの境界か端末で、インターネットから社内への通信と、社内から不正なサーバへの通信の両方について、不正アクセスをリアルタイムに検知・遮断する仕組みがある（UTM、EDR など。GuardDuty は AWS の中の検知だけで、遮断はしない）
- [ ] ネットワーク機器のログとアラートを分析し、担当者がインシデントかどうかを判断している
- [ ] 異常があれば速やかにアラートが出て、インシデントの速報レポートが作られ、通知される

## 6. インシデントへの対応（15 章）

**6-1-1 インシデント対応手順**

本: 15 章（初動、何を誰に伝えるか）、16 章（報告）／規程サンプル: 組織的対策 9（情報セキュリティインシデント対応及び事業継続管理）

- [ ] 発見・報告、初動、調査・対応、復旧、最終報告を含む対応手順がある
- [ ] 社内外（関係当局と所管省庁を含む）の連絡先と、報告・情報共有のルートを定めている
- [ ] インシデント発生時の、統括する役員と担当部署の役割・責任を定めている
- [ ] 連絡先・報告ルートと役割・責任を年 1 回点検している
- [ ] インシデントの報告フォーマットがある
- [ ] 年 1 回以上と、社内外で重大なインシデントが起きたときに、事例と対応策を社内で共有している

## 7. インシデントからの復旧（9・15 章）

**7-1-1 事業継続要件に沿った復旧準備**

本: 9 章（バックアップ）、15 章（事業継続）／規程サンプル: 技術的対策 5（リストア手順）

- [ ] 事業継続上重要なシステムについて、サイバー攻撃を念頭に、業務の目標復旧レベルを決め、そこまで回復するための対策（予備機やクラウドでの待機系、電話・ファクスなどによる人手での業務継続など）を整えている
