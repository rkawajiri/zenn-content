:::message
**最近のニュースから**

**侵入から被害までには時間がある（2025 年）**: アサヒグループでは、システム障害が起きる **約 10 日前** に攻撃者がネットワークに侵入していました。アスクルの調査報告では、初期侵入は 2025 年 6 月で、ランサムウェアが展開されたのは 10 月、つまり **約 4 か月間** 攻撃者が中にいたことになります。

**「うちも入られていないか」を確かめる時代（2026 年 10 月）**: 国内で不正アクセスによる情報漏えいが相次いだことを受け、JPCERT/CC や IPA などが注意喚起を出しました。そこでは、外部に公開している Web アプリやサービスを洗い出し、**ログに異常がないか、修正が未適用でないかを確かめる** ことが求められています。

侵害調査は、事件が起きた会社だけのものではありません。**何も起きていない今こそ、確かめる価値があります。**
:::

この章では、**侵害調査** を 2 つに分けて扱います。

| | 平時の侵害調査 | インシデント後の調査（フォレンジック） |
|---|---|---|
| 問い | **すでに入られていないか？** | **何が、いつから、どこまでやられたか？** |
| きっかけ | 注意喚起、使っている製品の脆弱性の悪用、委託先・SaaS の侵害、定期 | 検知、通報、脅迫、外部からの連絡 |
| 主な担い手 | 推進リーダー＋ツール（必要に応じて外部の侵害調査サービス） | 外部の調査会社（フォレンジック事業者）＋社内の窓口 |
| ゴール | 「痕跡はなかった（この範囲・期間で）」と言える記録、または早期発見 | 原因と影響範囲の特定、根絶、当局・顧客への報告、再発防止 |
| 似ているが違うもの | ペネトレーションテストは「入れる穴があるか」を探す。侵害調査は「実際に入られた痕跡があるか」を探す | 復旧作業は「元に戻す」。調査は「何が起きたかを明らかにする」 |

どちらにも共通する前提は、**調べられるだけの記録（ログ）が残っていること** です。まずそこから始めます。

## 前提: 調べられるだけのログがあるか

インシデントの後に「ログが残っていなかったので、影響範囲を特定できなかった」となると、**漏えいした可能性がある範囲をすべて「漏えいのおそれあり」として扱う** しかなくなります。顧客への通知や報告の範囲が広がり、被害も信用の毀損も大きくなります。

| ログ | 気をつけること | 備え |
|---|---|---|
| AWS CloudTrail | コンソールのイベント履歴は **90 日分** しか見られない | 組織の証跡で、ログアーカイブアカウントの S3 に長期保管する（オブジェクトロック推奨）。Athena や CloudTrail Lake で検索できるようにしておく |
| VPC フローログ・ロードバランサーのアクセスログ・WAF のログ | 既定では無効のものが多い | 公開しているシステムでは有効にして S3 に保管する |
| アプリケーションのログ（API のアクセスログ、認証のログ、管理画面の操作ログ） | 「誰が、どの API で、どのデータを取ったか」が残っていないことが多い | 利用者 ID、リクエスト元、対象のリソースを記録する。**大量取得の調査に必要** |
| データベースの監査ログ | 既定では無効 | 機密データを持つ DB では、少なくとも管理者の操作を記録する |
| GuardDuty の検知結果 | GuardDuty の中では **90 日** で消える | Security Hub や S3 に送って長期保管する |
| IdP（Entra ID / Google Workspace / Okta）のサインインログ | プランによって保持期間が短い | SIEM や S3 に転送して保管する |
| GitHub の監査ログ | Enterprise の場合で **180 日**。Git の操作のイベント（クローン・プッシュなど）は **7 日** | Enterprise ならストリーミングで外部に保管する |
| SaaS・VPN の操作ログ | 部署ごとに契約していて、誰も見ていないことがある | 重要な SaaS は管理者を決め、ログの取り出し方を確認しておく |

**目安**: 最低 1 年、できれば数年分を、**本番アカウントとは別の、改ざんできない場所** に置きます。侵入から発覚まで数か月かかる例もあることを考えると、90 日では足りません。ISMS や SCS 評価制度の証跡としても使えます。

## 平時の侵害調査

### いつやるか

- **注意喚起が出たとき**: 2026 年 10 月のように、同じ手口の被害が相次いでいるとき
- **使っている製品の脆弱性が悪用されたとき**: CISA の KEV（悪用が確認された脆弱性のカタログ）に載った、JPCERT/CC が注意喚起した、など。**パッチを当てる前に悪用されていなかったか** を確かめる
- **委託先・SaaS・クラウド事業者が侵害されたとき**: そこに預けていた認証情報やデータが使われていないか
- **担当者の交代、組織の統合（M&A）のとき**: 引き継いだ環境が汚れていないか
- **定期的に**: 年 1 回、または SATv2 の定期点検（7 章）と同じ四半期ごと

### どこまで遡るか

まず **直近 1 か月** を見て、気になるものがあれば **3 か月** に広げる、という進め方が現実的です（IPA の注意喚起の解説でも示されている方法です）。重大な脆弱性の悪用が疑われるときは、その脆弱性が公表される前まで遡ります。

### 何を見るか（自分でできる範囲）

**AWS**

- [ ] IAM の認証情報レポートで、**知らないユーザー・アクセスキー**、最近作られたもの、長く使われていなかったのに最近使われたものがないか
- [ ] CloudTrail で、次のような操作が **想定外の人・場所・時間** に行われていないか
  - ユーザー・アクセスキー・ロールの作成、ポリシーの付与（`CreateUser`、`CreateAccessKey`、`AttachUserPolicy`、`PutRolePolicy` など）
  - ログや検知の停止（`StopLogging`、`DeleteTrail`、GuardDuty の無効化など）
  - 公開・共有の設定変更（`PutBucketPolicy`、`ModifySnapshotAttribute`、`ModifyDBSnapshotAttribute` など）
  - 普段使わないリージョンでのリソース作成（暗号資産のマイニングによくある）
  - 見慣れない国・IP アドレスからの `ConsoleLogin`
- [ ] IAM Identity Center で、知らないユーザーや権限セットの変更がないか
- [ ] IAM Access Analyzer で、**外部アカウントや公開** のアクセスが増えていないか
- [ ] GuardDuty の検知結果を、**アーカイブ・抑制したものも含めて** 見直す。GuardDuty の拡張脅威検出（Extended Threat Detection）は、複数の段階にわたる攻撃をまとめて示してくれる

**ID（IdP・メール）**

- [ ] 見慣れない場所・端末からのサインイン、短時間に別の国からのサインイン
- [ ] MFA の再登録や、管理者権限の付与
- [ ] 身に覚えのない OAuth アプリへの同意
- [ ] メールの自動転送ルールの追加
- [ ] **無効にしたはずのアカウントの復活**、身に覚えのないアカウントの作成

**GitHub**

- [ ] 新しい個人アクセストークン、デプロイキー、SSH キー、GitHub App の追加
- [ ] 組織のオーナーの追加、リポジトリの公開範囲の変更
- [ ] GitHub Actions のワークフローの不審な変更、シークレットの追加・参照
- [ ] 普段と違う大量のクローンやダウンロード

**公開している Web アプリ・API**

- [ ] 同じ利用者・IP アドレスからの **大量のデータ取得**、連番の ID を順に取得するようなアクセス
- [ ] 公開アプリ（モバイルアプリを含む）が使う API への、アプリ以外からのアクセス
- [ ] 管理画面や BI ツールへの、外部からのアクセス
- [ ] エラーの急増（脆弱性を探しているときによく起きる）
- [ ] 未適用のセキュリティ修正がないか

**SaaS・VPN**

- [ ] 部署ごとに契約しているものも含めて、管理者アカウントの一覧と、最近のログイン
- [ ] VPN 機器のログイン履歴と、ファームウェアの更新状況（ランサムウェアの侵入経路として多い）

### 使える道具

| 道具 | 使いどころ |
|---|---|
| CloudTrail Lake / Athena | 長期間の CloudTrail を SQL で検索する |
| AWS Security Incident Response | 検知結果のトリアージと AI による調査。**脅威ハンティングは対象外** なので、平時の侵害調査の代わりにはならない |
| GuardDuty（拡張脅威検出）・Amazon Detective | 検知結果のつながりや、関係する IAM・IP の動きを可視化する |
| Wiz | 攻撃経路上にあるリソースから優先的に調べる。Wiz Defend や Blue Agent で検知の調査を支援する |
| GitHub の監査ログ | トークン・キー・権限の変更を調べる |
| Claude Code などの AI エージェント | 調査用のクエリを書く、大量のログを要約する、怪しい操作を洗い出す。**読み取り専用の権限** で、ログを外部に出してよいかのルールを確認したうえで使う |
| 外部の侵害調査サービス（コンプロマイズアセスメント） | 端末・ネットワーク・クラウドに収集ツールを置き、数週間分の活動を専門家が調べる。自社で見る力が足りないとき、重大な注意喚起が出たとき、M&A のときなどに |

### 結果を記録する

平時の侵害調査で何も見つからなかったとしても、**「いつ、どの範囲を、どの期間、どの方法で調べ、痕跡はなかった」** という記録は価値があります。経営への報告、取引先への説明、ISMS や SCS 評価制度の証跡になります。同時に、**ログがなくて調べられなかった範囲** も書いておきます。それが次の改善点です。

## インシデント後の調査（フォレンジック）

### 調査で明らかにすること

1. **何が起きたか**（攻撃の手口）
2. **いつから**（初期侵入の時期）
3. **どこまで**（影響を受けたシステム、アカウント、データ）
4. **どうやって入られたか**（侵入経路と根本原因）
5. **まだ中にいないか**（バックドアや、作られたアカウントが残っていないか）
6. **何が持ち出されたか**（個人情報・機密情報の範囲）

5 を確かめずに復旧すると、同じ攻撃者に再び入られます。6 は、顧客への通知と当局への報告の範囲を決めます。

サイバーセキュリティ経営ガイドライン Ver3.0 の **付録 C**（Excel）には、インシデントの原因調査で組織内で整理しておくべき項目が、「全インシデント共通」「情報漏えい」「ウイルス感染」「不正アクセス」「（D）DoS 攻撃」の表に分けてまとめられています。発生日・発覚日・発覚の経緯・原因と経路などの欄があるので、調査結果を経営に報告するときのひな型として使えます。

### 最初の 24 時間でやること（証拠を残す）

13 章の初動手順に加えて、調査のために次のことをします。

| 対象 | やること | やってはいけないこと |
|---|---|---|
| EC2 などのサーバー | セキュリティグループを差し替えてネットワークから隔離する。EBS のスナップショットを取る。可能ならメモリも取得する。タグで「調査中」と明示する | **すぐに削除・再起動・再構築する**（証拠が消える） |
| 認証情報 | 漏えいが疑われるアクセスキーを無効化し、ロールの既存セッションを失効させる | 無効化しただけで終わる（その鍵で何をされたかの調査が必要） |
| ログ | CloudTrail・フローログ・アプリのログを、**別アカウントにコピー** する。SaaS の監査ログは、保持期間が切れる前にエクスポートする | 攻撃者がアクセスできるかもしれない場所にだけ置いておく |
| 記録 | 時刻と、誰が何をしたかを残す（調査会社に渡す時系列の材料になる） | 記憶だけに頼る |

**調査会社には、できれば 24 時間以内に連絡し、作業を始めてもらう** のが望ましいとされています。証拠は時間とともに失われるからです。

### 外部の調査会社（フォレンジック事業者）

専任チームのない会社が、本格的なフォレンジックを自社だけで行うのは現実的ではありません。**平時に依頼先を決めておく** ことが最大の備えです。

- **依頼先の候補を決めておく**: サイバー保険に入っているなら、保険会社が提携している調査会社や、事故対応サービスの窓口をまず確認する。保険の補償に調査費用が含まれるか、事前の連絡が必要かも確かめる
- **AWS を使っているなら**: 調査会社がクラウドの調査に慣れているかを確かめる。あわせて、AWS 部分の一次対応役として **AWS Security Incident Response**（次の節）を検討する
- **費用と期間の目安**: ランサムウェアの調査で、**約 1 か月・数百万円規模** という例が紹介されています。対象の台数、クラウドの範囲、報告書の形式によって大きく変わるので、平時に見積もりの考え方を聞いておく
- **見積もりで確かめること**: 調査の範囲（端末・サーバー・クラウド・SaaS）、報告書の形式（経営向け・技術向け・当局向け）、当局への報告や顧客への説明の支援、復旧の支援の有無

### AWS Security Incident Response の位置づけ

AWS には、セキュリティインシデントへの対応を支援するマネージドサービス **AWS Security Incident Response** があります。専任チームのない会社にとって、AWS 部分の「夜間・休日も含めた一次対応役」として有力な選択肢です。

| 項目 | 内容 |
|---|---|
| 何をするか | GuardDuty と、Security Hub 経由で連携したサードパーティの検知ツールの **脅威の検知結果** を監視し、関連する検知結果をまとめ、重複を除いてトリアージする。**対応が必要なときだけ** 利用者に連絡する |
| AI による調査 | 調査用の AI エージェントが、複数の AWS のデータソースから証拠を集めて関連づけ、要約を示す（2025 年 11 月から、追加料金なしで全利用者に提供） |
| 人の支援 | AWS のセキュリティインシデント対応の専門家に 24 時間 365 日相談できる。利用者がエスカレーションしたケースは、初回対応の目標が 15 分 |
| ケース | サービスが自動で作るケース（プロアクティブ）と、利用者が作るケース（リアクティブ。AWS にエスカレーションするものと、自社で管理するものがある）。最終的にケースを閉じるのは利用者 |
| 報告 | 検知結果、トリアージの結果、作られたケースをまとめた月次レポート |
| 料金 | 取り込んだ検知結果の件数による従量課金で、**毎月 1 万件までは無料**。Enterprise Support などのプランを契約していれば追加料金なし（2025 年 11 月時点。最新は料金ページで確認） |
| 前提 | AWS Organizations の **すべての機能** が有効であること。委任管理者のアカウント（推奨）で有効にし、対象を組織全体または OU 単位で選ぶ |
| 言語 | 英語のサポートが基本。日本語のサポートは日本時間の営業時間内に限られる |

**できないこと** も、はっきり押さえておきます。ユーザーガイドでは、次のものは対象外とされています。

- **脅威ハンティング**（平時の侵害調査で、能動的に痕跡を探すこと）
- **ディスクのフォレンジック分析**
- **法務・規制対応の助言**（個人情報保護委員会への報告など）
- **修復作業の実行**（推奨は出すが、作業は利用者が行う）
- **攻撃者の特定**

つまり、AWS Security Incident Response は **調査会社の代わりではなく、AWS の中で起きていることを早く正しく判断するための一次対応役** です。この本の組み合わせでは、次のように位置づけます。

| 場面 | 担い手 |
|---|---|
| GuardDuty の検知の一次判断（夜間・休日を含む） | **AWS Security Incident Response** |
| AWS のログにもとづく調査と、封じ込めの推奨 | **AWS Security Incident Response**（必要に応じて自社のエンジニア） |
| 平時の侵害調査（脅威ハンティング） | 自社（この章のチェックリスト）＋ 外部の侵害調査サービス |
| 端末・サーバーのディスクのフォレンジック、影響範囲の確定、当局への報告の支援 | **外部の調査会社** |
| 報告・公表・身代金への対応などの判断 | 自社の経営・責任者・法務・広報 |

導入するなら、Lv2 で Organizations と GuardDuty を全体に行き渡らせた後が適切です。検知結果を取り込む仕組みなので、**GuardDuty が全アカウントで有効になっていること** が前提になります。

### 社内でやること、任せること

| 社内（推進リーダー・責任者） | 外部（調査会社など） |
|---|---|
| 経営への報告と判断（事業を止めるか、身代金に応じないか、公表するか） | 証拠の解析、攻撃の手口と時系列の特定 |
| 調査会社への情報提供（構成図、資産の一覧、ログの場所、関係者） | 侵入経路と根本原因の特定 |
| 当局・顧客・取引先への連絡（法務・広報と） | 影響範囲（持ち出されたデータ）の推定 |
| 復旧の判断と、業務の代替手段 | 根絶の確認、再発防止策の提案 |

4 章のチェックシートや 15 章の「最初の 90 日」で作った **資産の一覧、構成図、ログの場所** は、ここで調査の速さを大きく左右します。

### 報告

- **個人情報保護委員会への報告**: 不正アクセスで個人データが漏えいした（またはそのおそれがある）場合、**速報**（概ね 3〜5 日以内）と **確報**（原則 30 日以内、不正の目的によるものは 60 日以内）が必要です。調査の結果を待たずに、分かっている範囲で速報を出します。
- **基幹インフラ事業者**: 能動的サイバー防御の関連法により、所管の当局への報告義務があります。
- **取引先**: 契約で報告義務が決まっていることが多いので、平時に確認しておきます。
- **調査報告書の公表**: アスクルは、攻撃の手口や初動対応を時系列でまとめた報告書を公表しました。どこまで公表するかは経営判断ですが、**根本原因と再発防止策を説明できるだけの調査** をしておくことが、信頼の回復につながります。

個人情報保護法サイバーセキュリティ連絡会は 2026 年 1 月に「[不正アクセス発生時のフォレンジック調査の有効活用に向けた着眼点](https://www.ppc.go.jp/files/pdf/260116_forensics_keypoints.pdf)」も公表しています（警察庁の広報誌でも紹介されています）。調査を依頼する前に目を通しておくと、何を頼めばよいかが整理できます。

## レベル別の備え

| レベル | 平時の侵害調査 | インシデント後の調査 |
|---|---|---|
