:::message
**最近のニュースから**

**AI コーディングエージェントを狙う攻撃（2026 年）**: 2026 年 6 月、AI コーディングエージェントが MCP サーバー経由で読み込んだエラー監視サービスの内容に命令を紛れ込ませ、**開発者の認証情報を盗ませる** 攻撃手法が研究者から報告されました。ほかにも、MCP サーバーの脆弱性や、AI エージェントの安全装置を回避する手法の報告が相次いでいます。

IPA の 10 大脅威 2026 で「AI の利用をめぐるサイバーリスク」が初めて 3 位に入ったのは、こうした流れを受けたものです。
:::

12 章では「AI で守る」話をしました。この章は逆に、**AI を使う・作ることで生まれるリスク** の話です。IPA の 10 大脅威 2026 で「AI の利用をめぐるサイバーリスク」が初めて 3 位に入ったように、これはもう将来の話ではありません。

## 3 つの立場

AI のリスクは、会社がどの立場で AI に関わるかで変わります。AI 事業者ガイドライン（4 章）も、開発者・提供者・利用者の 3 つの立場を分けています。

| 立場 | 例 | 主なリスク |
|---|---|---|
| **利用者** | 社員が ChatGPT / Claude / Copilot を業務で使う | 機密情報の入力、出力の誤り（ハルシネーション）をそのまま使う、権利侵害 |
| **開発者としての利用者** | 開発者が Claude Code などの AI コーディングエージェントを使う | エージェントへのプロンプトインジェクション、認証情報の漏えい、危険なコマンドの実行、脆弱なコードの混入 |
| **提供者** | 自社のサービスに AI 機能（チャットボット、AI エージェント）を組み込む | 顧客データの漏えい、AI 機能の乗っ取り、過剰な権限による被害、コストの暴走 |

## 参考にするフレームワーク

### OWASP Top 10 for LLM Applications 2025

大規模言語モデル（LLM）を使ったアプリケーションの代表的なリスクです。

| # | リスク | 一言で |
|---|---|---|
| LLM01 | プロンプトインジェクション | 入力に紛れ込ませた命令で AI を操る |
| LLM02 | 機密情報の漏えい | AI が知っている・扱う情報が漏れる |
| LLM03 | サプライチェーン | モデル・データ・ライブラリ・プラグインの汚染 |
| LLM04 | データとモデルの汚染（ポイズニング） | 学習データや参照データを汚して出力をゆがめる |
| LLM05 | 不適切な出力の扱い | AI の出力を検証せずに実行・表示する |
| LLM06 | 過剰な自律性（Excessive Agency） | AI に必要以上の権限や機能を与える |
| LLM07 | システムプロンプトの漏えい | 内部の指示や秘密が漏れる |
| LLM08 | ベクトルと埋め込みの弱点 | RAG の検索データの権限や汚染の問題 |
| LLM09 | 誤情報 | もっともらしい誤りを信じてしまう |
| LLM10 | 無制限な消費 | 大量のリクエストによるコストやリソースの枯渇 |

### OWASP Top 10 for Agentic Applications 2026

2025 年 12 月に公開された、**AI エージェント** に特化したリスクの一覧です（ASI01〜ASI10）。

| # | リスク | 一言で |
|---|---|---|
| ASI01 | エージェントの目的の乗っ取り（Goal Hijack） | エージェントが読む内容（メール、Web、ドキュメント、ツールの出力）でエージェントの目的を書き換える |
| ASI02 | ツールの誤用・悪用 | 与えられたツールを意図しない形で使わせる |
| ASI03 | ID と権限の悪用 | エージェントの持つ認証情報や権限を悪用する |
| ASI04 | エージェントのサプライチェーンの脆弱性 | MCP サーバー、プラグイン、外部エージェントなどの汚染 |
| ASI05 | 想定外のコード実行 | エージェントに任意のコードを実行させる |
| ASI06 | メモリとコンテキストの汚染 | エージェントの記憶や参照情報を汚す |
| ASI07 | 安全でないエージェント間通信 | エージェント同士のやりとりの改ざん・なりすまし |
| ASI08 | 連鎖的な障害 | 1 つのエージェントの誤りが連鎖して大きな被害になる |
| ASI09 | 人とエージェントの信頼の悪用 | 人がエージェントを過信することにつけ込む |
| ASI10 | 暴走するエージェント（Rogue Agents） | 意図から外れて動き続けるエージェント |

GMO Flatt Security が 2026 年 9 月の「Product Security Square」で発表した「AI エージェントの開発・提供におけるセキュリティリスクの論点と対策」でも、この一覧を軸に論点が整理されています（16 章）。

:::message
**一番大事な考え方**: AI エージェントの安全性は「AI が賢いかどうか」ではなく、**「AI が騙されたときに、何ができてしまうか」** で決まります。プロンプトインジェクションを完全に防ぐ方法はまだないので、**騙されても被害が小さくなるように権限と環境を絞る** のが基本です。「信頼できない入力を読む」「機密データに触れる」「外に送信できる」の 3 つを、1 つのエージェントに同時に持たせないようにするのが有効な目安です。
:::

## 立場別の対策

### 1. 利用者として（全社員）

**Lv1**
- 会社として契約した AI サービス（入力が学習に使われない設定のもの）を用意し、それ以外の利用を原則禁止する
- **入力してはいけない情報** を決める（例: 顧客の個人情報、取引先から預かった機密情報、未公開の財務情報、認証情報）
- 「AI の出力は必ず人が確かめる」をルールにする

**Lv2**
- AI 利用ガイドラインを文書化する（AI 事業者ガイドラインの「AI 利用者」向けの項目と、IPA の 10 大脅威の解説を下敷きにする）
- 社員向けの短い教育（10〜15 分）を行う
- 社内で使われている AI サービスの一覧を作る（シャドー AI の把握）

**Lv3**
- SSO と監査ログを使える法人向けプランに統一する
- データ損失防止（DLP）の仕組みで、機密情報の入力を検知する

### 2. 開発者として（AI コーディングエージェント）

AI コーディングエージェントは、開発者の PC やクラウド上で **コマンドを実行し、ファイルを読み書きし、ネットワークにアクセスできる** ため、攻撃者から見ると「開発者の権限で動く、騙せるかもしれないプログラム」です。

| 対策 | 具体例 |
|---|---|
| 自動承認の範囲を絞る | Claude Code の権限設定（allow / deny ルール）で、危険なコマンドや本番環境への操作は毎回確認する。組織として **管理された設定（managed settings）** で配布する |
| サンドボックスで動かす | Claude Code のサンドボックス機能、開発用コンテナ、クラウドの隔離された環境で動かし、ファイルとネットワークのアクセスを制限する |
| 認証情報を渡さない | エージェントの環境に本番の認証情報を置かない。AWS は検証環境の、権限を絞った一時的な認証情報だけにする |
| MCP サーバーを管理する | 使ってよい MCP サーバーを許可リストで管理し、出所の分からないものを使わない |
| 信頼できない入力に注意 | 外部のリポジトリ、Issue、Web ページには、エージェントへの命令が仕込まれている可能性がある |
| 生成コードもレビューする | AI が書いたコードも、人が書いたコードと同じ PR のチェック（11 章）とレビューを通す |
| ログを残す | エージェントが何を実行したかを記録する |

### 3. 提供者として（自社サービスの AI 機能）

AWS で AI 機能を作る場合の対策の例です。

| リスク | 対策 | AWS の道具の例 |
|---|---|---|
| プロンプトインジェクション、有害な出力 | 入出力のフィルタ、システムプロンプトと利用者の入力の分離 | **Amazon Bedrock Guardrails** |
| 過剰な権限（LLM06 / ASI03） | エージェントが使うツールと権限を最小にする。重要な操作は人の承認を必須にする | IAM、**Bedrock AgentCore** の ID と権限の管理 |
| RAG の権限漏れ（LLM08） | 検索データに、元のデータの閲覧権限を反映する | ナレッジベースのメタデータによる絞り込み |
| 不適切な出力の扱い（LLM05） | AI の出力をそのまま SQL・コマンド・HTML として使わない | 通常のアプリケーションの対策 |
| コストの暴走（LLM10） | 利用者ごとのレート制限と予算アラート | API Gateway、AWS Budgets |
| AI 資産の把握漏れ | 組織内の AI 資産を一覧化し、設定ミスを検出する | **Security Hub の AI インベントリ**、Wiz の AI-SPM |
| AI への攻撃の検知 | AI ワークロードへの不審な操作を検知する | **GuardDuty AI Protection** |
| 監査と調査 | プロンプトと応答、ツールの呼び出しを記録する | Bedrock のモデル呼び出しログ、CloudTrail |

Security Hub の AI インベントリは、Bedrock・AgentCore・SageMaker の資産を自動で見つけ、関連する検知結果と結びつけてくれます。ただし、これは「把握と優先順位づけ」の道具であり、プロンプトインジェクションそのものを防ぐものではありません。Guardrails などの対策と組み合わせて使います。

**Lv3〜Lv4** では、AI 機能のリリース前に OWASP の 2 つの一覧を使った脅威モデリングとレッドチーミング（攻撃のテスト）を行い、12 章の AI 診断ツールでも AI 機能を対象に含めます。

## AI 利用ガイドラインのひな型（最小版）

最初は、次の 1 ページで十分です。

```markdown
# AI 利用ガイドライン（v0.1）

## 使ってよい AI サービス
- 会社が契約した ○○、△△（入力が学習に使われない設定）
- それ以外の AI サービスを業務で使うときは、事前にセキュリティ担当に相談する

## 入力してはいけない情報
- 顧客・取引先の個人情報、取引先から預かった機密情報
- パスワード、API キーなどの認証情報
- 未公開の財務情報・人事情報

## 出力の扱い
- AI の出力は、必ず人が内容を確かめてから使う
- 社外に出す文書・コードは、通常のレビューを通す
- 他者の権利（著作権など）を侵害していないか注意する

## AI コーディングエージェント
- 会社が配布した設定で使う。自動承認の範囲を勝手に広げない
- 本番環境の認証情報がある環境では使わない
- 使ってよい MCP サーバー・プラグインは一覧のものだけ

## 困ったとき・事故が起きたとき
- セキュリティ担当（#security チャンネル）にすぐ連絡する
```
