:::message
**最近のニュースから**

**警察庁（2026 年 9 月）** によると、2026 年上半期のランサムウェア被害の報告は **123 件** で、半期で過去最多でした。うち 79 件が中小企業です。脆弱性を探すなどの不審なアクセスも、前年同期比で約 5 割増えています。

自社の環境は、攻撃者から **毎日外から点検されている** と考えるべきです。それなら自社も、攻撃者より先に、定期的に自分を点検しておく必要があります。この章では SATv2 を使った「健康診断」を扱います。
:::

AWS アカウントがたくさんあり、それぞれ違う人が作ってきた会社では、「どこにどんな穴があるのか」を把握するだけで大変です。この章では、AWS が無償で公開している **SATv2** を、一度きりの診断ではなく **定期的な健康診断** として使う方法を扱います。

## SATv2 とは

**SATv2（Self-Service Security Assessment Solution v2）** は、AWS Labs が GitHub で公開しているソリューションです（[awslabs/aws-security-assessment-solution](https://github.com/awslabs/aws-security-assessment-solution)）。オープンソースのセキュリティ診断ツール **Prowler** を自社の AWS アカウントの中で動かし、**1 つのアカウント、または AWS Organizations 配下の全アカウント** を一度に診断します。

| 項目 | 内容 |
|---|---|
| 位置づけ | **ある時点の評価**（ポイントインタイム評価）。常時監視の道具ではない |
| 仕組み | CloudFormation で CodeBuild などを作り、各アカウントに配った **読み取り専用** のロールで Prowler が診断する |
| 所要時間 | デプロイ・診断とも数分〜（リソース数と診断の種類による） |
| 費用 | 無料利用枠に収まるよう設計。超えても 1 回あたり 1 ドル未満の見込み（README より） |
| 出力 | アカウントごとの HTML レポート、CSV、JSON / OCSF。オプションで Athena による全社集計とダッシュボード |

診断の種類は 3 つあります。

| 種類 | 内容 | 使いどころ |
|---|---|---|
| Basic | ルートの MFA、公開 S3、開いたセキュリティグループなど、基本的なチェックだけ | 経営への説明用、最初の 1 回 |
| **Intermediate**（既定） | 重大度 Critical / High のチェックすべて | 定期点検の基本 |
| Full | 650 以上のチェックすべて | Lv2 以降の詳しい点検 |

AWS の「Security Health Improvement Program（SHIP）」というワークショップでも、最初のステップとして SATv2 による評価が使われています。デプロイの手順やパラメーターは README にまとまっているので、この章では **結果をどう読み、どう使うか** に集中します。

## Security Hub や Wiz があるのに、なぜ SATv2 なのか

常時の点検は、Security Hub（FSBP 標準）や Wiz の役割です（7 章の役割分担）。それでも SATv2 を定期的に使う理由は 3 つあります。

1. **別の目で確かめる**: 同じツールだけを見ていると、そのツールが見ていない穴に気づけません。Prowler は独立したチェックの集まりなので、抜けの確認になります。
2. **全アカウントが本当に対象か確かめる**: Security Hub や Wiz の連携から漏れているアカウントがあっても、SATv2 で Organizations 全体を診断すると見つかります。
3. **改善の推移を、同じ物差しで記録する**: 同じ条件で四半期ごとに診断すると、件数の推移がそのまま「どれだけ良くなったか」の証拠になります。経営への報告や、ISMS・SCS 評価制度の証跡にも使えます。

## 結果の読み方

結果は数百〜数千件になることが多いです。全部を一度に見ようとせず、次の順番で絞ります。

1. **Critical / High で、インターネットから到達できるもの**（公開 S3、0.0.0.0/0 のセキュリティグループ、公開スナップショットなど）
2. **ID まわり**（ルートの MFA・アクセスキー、古いアクセスキー、管理者権限を持つ IAM ユーザー）
3. **検知とログ**（CloudTrail・GuardDuty・Config が無効なアカウントやリージョン）
4. それ以外の Critical / High
5. Medium 以下は、Wiz / Security Hub の通常の運用に任せる

### アカウント別に並べる

もう 1 つの有効な見方は、**アカウントごとの件数** です。件数の多いアカウントは、たいてい次のどれかです。

- 昔の検証用で、持ち主がいない（→ 削除するか、持ち主を決める）
- Control Tower や SCP の管理から外れている（→ 管理下に入れる）
- 特定のチームが急いで作った（→ そのチームと一緒に直し、標準構成を共有する）

**持ち主のいないアカウント** は、削除するか持ち主を決めるかを経営判断にかけます。これだけで件数が大きく減ることがよくあります。

### Wiz / Security Hub の結果と照らし合わせる

SATv2 で見つかったのに Wiz や Security Hub で出ていない問題があれば、次のどれかです。

- そのアカウントが連携から漏れている（→ 連携を直す。これが一番重要）
- Wiz / Security Hub 側で抑制（suppress）している（→ 抑制の理由が記録されているか確かめる）
- チェックの観点が違う（→ 必要なら Wiz / Security Hub 側にルールを追加する）

## 四半期ごとの運用

| タイミング | やること |
|---|---|
| 四半期の初め | 同じ診断の種類（Intermediate など）・同じ範囲で SATv2 を実行する |
| 実行直後 | 前回との差分を見る。**新しく増えたもの** と、**直ったもの** に分ける |
| 週次レビュー | 新しく増えた Critical / High を、持ち主のチームに割り振る |
| 四半期の終わり | 件数の推移を、6 章のチェックシートと一緒に経営に報告する |

## 注意すること

:::message alert
**結果は機密情報です。** レポートは「自社のどこに穴があるか」の一覧なので、攻撃者にとって最も価値のある情報の 1 つです。共有範囲を絞り、S3 の署名付き URL で共有するときは、URL に作成者の権限が乗ることと有効期限に注意してください。
:::

- **使い終わったら片付ける**: SATv2 は「使ったら消す」前提のソリューションです。読み取り専用とはいえ、全アカウントを読めるロールを残しておくのはリスクです。定期的に使う場合も、実行のたびにデプロイし、終わったらスタックと StackSet を削除する運用にすると安全です。結果の S3 バケットは自動では消えないので、保管するものを決めて管理します。
- **シークレットの検出は既定で対象外**: Lambda のコードや EC2 のユーザーデータなど、中身を読んでシークレットを探すチェックは既定でスキップされます。シークレットの検出は GitHub のシークレットスキャン（11 章）などで補います。
- **AWS の設定以外は見えない**: アプリケーションの脆弱性（12 章）、GitHub、SaaS、社員の PC は対象外です。
