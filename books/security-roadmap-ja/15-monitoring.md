:::message
**最近のニュースから**

**アスクル（2025 年 10 月）** の調査報告によると、攻撃者は偵察と認証情報の収集を進め、EDR などの対策ソフトを無効化してから、ランサムウェアを展開しました。報告書は原因として、侵害されたデータセンターのサーバーに EDR が入っておらず、**24 時間の監視もなかった** ことを挙げています。同社は再発防止策として、全サーバーへの EDR の導入と 24 時間の監視を示しました。

検知の道具があっても、アラートを誰も見ていなければ、攻撃者は準備を最後まで進められます。
:::

第 5 部では、攻撃に気づき、対応し、計画を立て直す部分を扱います。最初のこの章は、**気づくまで** の話です。

第 3 部と第 4 部で、EDR、IdP、GuardDuty など、攻撃の兆しを知らせる道具を見てきました。ただ、道具が知らせても、誰かが見て判断しなければ何も起きません。専任チームのない会社では、「アラートは出ていたが、誰も見ていなかった」「夜間に出て、気づいたのは翌週だった」が起こりがちです。この章では、アラートの集め方、誰がいつ見るか、届いたら何を確かめるか、夜間・休日をどうするかを決めます。

## 2 種類の知らせを分ける

検知の道具が出す知らせには、性質の違う 2 種類があります。同じ扱いにすると、どちらかが埋もれます。

| | 直すべき問題 | いま起きているかもしれない攻撃 |
|---|---|---|
| 例 | 設定ミス、脆弱性、古い OS（Security Hub、Inspector、SATv2、CNAPP、Dependabot） | 不審なサインイン、マルウェアの検知、不審な通信、ログや EDR の停止（IdP、EDR、UTM、GuardDuty） |
| いつ見るか | 週次レビュー（6 章） | 届いたらすぐ、少なくともその日のうちに |
| 誰が直すか | 持ち主のチームが、期限（5 章の SLA）までに | 見た人がまず判断し、必要なら初動（16 章）に移る |

この章で扱うのは、右の列です。

## 何を見張るか

| 見張る場所 | 主な知らせ | 道具の例 | 章 |
|---|---|---|---|
| 社員の ID | 見慣れない場所からのサインイン、MFA の再登録、管理者権限の付与、緊急用アカウントの使用 | IdP | 7 |
| 社員の PC | マルウェアや不審な動きの検知、EDR の停止 | EDR、ウイルス対策 | 8 |
| メール | 外部への自動転送ルールの追加 | メールの管理機能 | 8 |
| ネットワークの境界 | 不正な通信の検知・遮断 | UTM、ファイアウォールの IPS 機能 | 8 |
| 業務の SaaS | 大量のダウンロード、社外への共有 | SaaS の監査ログとアラート | 8 |
| AWS | GuardDuty の重大度「高」、ルートユーザーの利用、ログや検知の停止 | GuardDuty、Security Hub、CNAPP の実行時の検知（Wiz Defend など） | 9・11 |
| GitHub | シークレットの検出、組織のオーナーの追加 | GitHub のアラート、監査ログ | 12 |

SCS 評価制度 ★3 の 5-1-1 では、ネットワークの境界か端末で不正な通信をリアルタイムに検知・遮断し、アラートを担当者が分析してインシデントかどうかを判断し、速やかに通知することが求められています（20 章）。道具を入れるだけでなく、**誰が判断するか** までが求められている、ということです。

## 集める先を 1 つにする

最初の一歩は、知らせを **1 か所に集める** ことです。

- **チャットのチャンネルか、共有のメールアドレスに集める**: 担当者個人の受信箱に送らない。休暇や退職で止まるうえ、他の人が気づけない
- **最初は重大なものだけにする**: GuardDuty の重大度「高」、EDR の重大な検知、IdP の危険なサインイン、ログや EDR の停止。件数が多すぎると、誰も見なくなる
- **AWS の中は Security Hub で集める**: AWS の検知結果は、Security Hub で 1 か所に集めてから通知できる（9 章）
- **誰が見るかを決める**: 平日の日中は誰が見るか、その人がいないときは誰か、を決めてチャンネルの説明に書いておく

複数のログをまたいで調べたくなったら SIEM が候補になりますが、最初から必要なわけではありません（この章の後半の「SIEM は必要か」）。

## 届いたら、まず何を確かめるか

知らせが届いたら、次の 4 つを順に確かめます。最初から完璧に調べる必要はなく、**インシデントとして扱うかどうか** を早く決めることが目的です。

1. **本物か**: 本人や持ち主に確認する。予定された作業や、出張先からのログインではないか
2. **どこまで広がりうるか**: 管理者のアカウントか、本番環境か、機密情報に届くか
3. **いま止める必要があるか**: 端末をネットワークから切り離す（EDR の隔離機能）、アカウントを止める、アクセスキーを無効にする
4. **インシデントとして扱うか**: 扱うなら、16 章の初動手順に移る

判断の結果は、誤検知だった場合も含めて記録します。「何が届き、誰が、いつ、どう判断したか」の記録は、★3 の証跡になるだけでなく、同じ誤検知を減らすための材料にもなります。

## 見張りが止められていないか

攻撃者は、暗号化や持ち出しの前に、見張りを止めようとします。アスクルの事案でも、EDR などが無効化されていました。**見張りそのものが止まったこと** に気づけるようにしておきます。

- **EDR**: 停止、アンインストール、一定期間報告が来ない端末を通知する（8 章）
- **AWS**: CloudTrail の記録の停止や GuardDuty の無効化は、SCP でできないようにし（9 章）、それでも起きたら通知が来るようにする
- **IdP・メール**: 監査ログの設定変更、管理者の追加を通知する

もう 1 つ大事なのは、**静かすぎることを疑う** ことです。何週間もアラートが 1 件も来ないのは、安全だからではなく、通知の経路が壊れているからかもしれません。GuardDuty には[サンプルの検知結果を作る機能](https://docs.aws.amazon.com/guardduty/latest/ug/sample_findings.html)があり、ウイルス対策ソフトや EDR は [EICAR のテスト用ファイル](https://www.eicar.org/download-anti-malware-testfile/)（実害のない、検知の確認用のファイル）で検知を確かめられます。四半期に 1 回などの頻度で、テスト用の知らせが本当にチャンネルに届くかを確かめます。

## 夜間・休日をどうするか

担当者がいない夜間や休日は、攻撃者にとって都合のよい時間です。気づくのが休み明けになれば、その分だけ準備を進められてしまいます。専任チームのない会社では、次のどれか、または組み合わせを選びます。

| やり方 | 向いている会社 | 気をつけること |
|---|---|---|
| 営業時間だけ見る（重大なものだけスマートフォンに通知） | Lv1〜Lv2。担当者が 1〜2 名 | 気づくのは翌朝や休み明けになる。人がいなくても被害が広がりにくいよう、道具が自動で止める設定を使う。ただし自動の隔離は、誤検知でも業務を止める。PC は自動で隔離し、サーバーは通知だけにする、のように対象で分ける |
| 社内の当番（オンコール） | 担当者や情報システム部門のメンバーが複数いる | 一人に寄せると続かない。交代のルールと、呼び出されたときの判断の範囲を決める。待機や呼び出しの扱い（勤務時間や手当）は、人事・総務と決めておく |
| MDR（EDR などの製品と組み合わせて、外部の専門家が 24 時間見て一次対応までするサービス） | 端末やサーバーが多く、夜間・休日に人を割けない | どこまでやってくれるか（連絡だけか、隔離まで行うか）。対象は端末だけか、サーバー・IdP・クラウドも含むか |
| MSSP・SOC のサービス（複数の機器やログを外部が監視するサービス） | 境界の機器、端末、クラウドを広く見てほしい | 取り込むログの範囲と費用。誤検知をどこまで絞ってから連絡してくれるか |
| AWS Security Incident Response（AWS の検知の一次対応） | AWS の比重が大きい | 対象は AWS の中の検知で、端末や SaaS は見ない。脅威ハンティングや修復作業もしない。日本語のサポートは日本時間の営業時間内に限られ、夜間・休日は英語でのやり取りになる（17 章） |

### 外部に任せるときに決めておくこと

外部に任せる場合でも、**連絡を受けて判断する人** は社内に必要です。事業を止めるか、公表するかといった判断は、外部には任せられません。夜間・休日の連絡先と判断できる人を、連絡網（16 章）に入れておきます。

そのうえで、**外部が社内に聞かずにやってよいこと** を、契約と手順で先に決めておきます。決めていないと、夜中に「この端末を隔離してよいですか」と連絡が来ても、判断できる人がつかまるまで何も止まりません。

| 対応 | 決め方の例 |
|---|---|
| PC の隔離 | 聞かずにやってよい。やったら連絡する |
| アカウントの一時停止 | 一般社員は聞かずにやってよい。管理者と役員は連絡して判断を待つ |
| サーバーの隔離・停止 | 業務が止まるので、必ず連絡して判断を待つ |
| 連絡がつかないとき | 何分待って、次に誰に連絡するか |

### 組み合わせたときの抜けを確かめる

よくある組み合わせは、「端末は MDR、AWS は AWS Security Incident Response」です。この組み合わせでは、IdP の不審なサインインや SaaS の大量ダウンロードを、夜間に誰も見ていない、ということが起きます。

この章の「何を見張るか」の表の行ごとに、**平日の日中に誰が見るか、夜間・休日に誰が見るか** を書き込んでみてください。空欄の行が、見張りの抜けです。空欄を全部埋める必要はありませんが、「夜間は見ない」と決めた行は、休み明けに最初に確かめる、という手順にしておきます。

外部のサービスの候補を探すときは、IPA の「情報セキュリティサービス基準適合サービスリスト」の「セキュリティ監視・運用」の分野が出発点になります（17 章）。

## SIEM は必要か

ログを集める話になると、SIEM（複数のログを集めて検索・相関分析し、アラートを出す製品）を入れるべきか、という問いが出てきます。専任チームのない会社では、次の順で考えるのが現実的です。

| 段階 | やり方 | 向いている状態 |
|---|---|---|
| Lv2 | ログを S3 などの消せない場所に集め、必要なときに Athena や CloudTrail Lake で検索する。リアルタイムの検知は GuardDuty と IdP・EDR の標準のアラートに任せる | まず「調べられる」ことが目標のとき |
| Lv3 | AWS・IdP・EDR・SaaS のログをまたいで相関を見たくなったら、SIEM を検討する。AWS なら、[Amazon Security Lake](https://docs.aws.amazon.com/security-lake/latest/userguide/what-is-security-lake.html) でログを OCSF（共通のスキーマ）にそろえてから、SIEM に購読させる方法もある | 週次レビューが回り、複数のログを突き合わせる必要が出てきたとき |
| Lv3〜Lv4 | 24 時間の監視が必要なら、SIEM を自分で運用するより、MDR / MSSP に監視ごと任せる | 夜間・休日の検知に人を割けないとき |

SIEM は、取り込むログの量に応じて費用が大きくなり、検知ルールを育てる人も必要です。「SIEM を入れたが、誰もアラートを見ていない」は、6 章の「入れたのに回らない」の典型です。入れる前に、誰がアラートを見るかを決めます。
## レベル別の進め方

| レベル | やること |
|---|---|
| Lv1 | 重大な知らせ（GuardDuty の重大度「高」、ウイルス対策や EDR の検知、IdP の危険なサインイン）が、決まったチャンネルに届き、誰が見るかが決まっている |
| Lv2 | 見張る場所の一覧があり、知らせが 1 か所に集まる。届いたら確かめることの手順があり、判断を記録している（★3 の 5-1-1）。EDR やログの停止に気づける。夜間・休日の方針を決めている |
| Lv3 | 夜間・休日も一次対応できる（当番、MDR、AWS Security Incident Response など）。テスト用の知らせで、届くことを定期的に確かめている。複数のログをまたいで見る必要があれば SIEM を検討する |
| Lv4 | 検知から封じ込めの一部（端末の隔離、キーの無効化など）を自動化している。気づくまでの時間を測り、改善している |

## よくある落とし穴

- **個人宛てに届いている**: 担当者の休暇や退職で、知らせが誰にも届かなくなります。共有のチャンネルに集めます。
- **多すぎて誰も見なくなる**: 最初は重大なものだけに絞り、慣れてから広げます。
- **外部に任せたのに、受け手がいない**: MDR から夜中に連絡が来ても、社内で判断できる人につながらなければ止められません。
- **静かなのは安全だと思う**: 通知の経路が壊れていないかを、テスト用の知らせで確かめます。
