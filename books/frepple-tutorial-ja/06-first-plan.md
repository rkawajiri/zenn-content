---
title: "最初の計画とレポートの読み方"
---

この章のゴール: 5 章のモデルで最初の計画（制約なし）を作り、各レポートで結果を読めるようになる。

:::message
**この章で学べる計画の考え方**

- 制約なし計画は MRP（受注から、必要な部品・製造・購買の量とタイミングを逆算する計算）に近く、すべての受注を納期どおりに満たす計画になる
- 実行できるかどうかは、問題（警告）として別に示される
- 計画は、需要・在庫・能力・例外の 4 つの視点で検証する
:::

## 計画を生成する

管理（Admin）メニューの **実行**（Execute）を開き、「計画を作成」（Create a plan）カードを使います。まずは違いを体感するために、**制約なし** で実行します。

1. 「Planning steps」（未訳で英語のまま）で「サプライチェーンを生成」（Generate supply plan）にチェックが入っていることを確認します。これがオフだと、購入オーダー（PO）などの供給計画が生成されません。（「予測を作成」（Generate forecast）は需要予測の機能です。13 章で扱うので、いまはチェックが入っていたら外します。）
2. 「Plan type」（英語のまま）で「Unconstrained plan」を選びます。
3. 「制約」（Constraints）の 3 つ（Capacity / Manufacturing lead time / Purchasing lead time。ラベルは英語のまま）は、すべてオフにします。
4. `起動`（Launch）を押します。

![実行画面の「計画を作成」カード](/images/frepple-tutorial-ja/execute-create-plan.jpg)

計画の生成は、このモデルなら数秒で終わります。画面上部のステータス欄が `完了`（Done）になれば完了です。タスクは非同期に実行され、ステータス欄は 5 秒ごとに更新されます。

### コマンドで実行する（任意）

画面の代わりに Web API でも、同じ計画を実行できます。以降の章では、繰り返し実行するので、この方法を使います。

```bash
cd examples/frepple-api    # リポジトリのルートから。5 章で setup-model.sh を使った場合は、すでにこのフォルダにいます
./plan.sh "plantype=2&constraint=0&env=supply"
# task 6: Done (6s)
```

`plan.sh` は Web API（`POST /execute/api/runplan/`）を呼び、終わるまで待つスクリプトです。クエリの意味は次のとおりです。

| パラメータ | 意味 |
|---|---|
| `plantype=2` | 制約なし計画（1 なら制約あり計画） |
| `constraint=0` | 制約をすべてオフ。オンにするときは `capa,mfg_lt,po_lt` のように書く |
| `env=supply` | 「サプライチェーンを生成」に対応 |

:::message
`docker exec … frepplectl runplan` でも計画は実行できますが、9.17.0 では計画が終わってもコマンドが戻ってきません。この本では使いません。
:::

## 計画が終わったら: 画面で結果を見る

計画が `完了` になったら、次の順に画面を開きます。メニューは、画面上部の「販売」「在庫」「能力」「購入」「製造」「管理」です。URL を直接入力しても開けます（`http://localhost:9000` に続けて入力します）。

### 1. 問題レポート: 「現実には守れない所」を見る

1. 上部の **能力** メニューを開き、**問題レポート**（Problem report）を選びます。URL は `/problem/?entity=capacity` です。
2. 一覧の 1 行を確認します。「名前」が `overload`、「所有者」が `workbench`、「記述」が `Resource 'workbench' has capacity shortage of 2` になっているはずです。
3. 「開始日」と「終了日」が、能力オーバーになっている期間です。所有者の横の矢印から、リソースの詳細に移れます。

![問題レポート。作業台（workbench）の能力オーバーが 1 件出ている](/images/frepple-tutorial-ja/first-plan-problem-report.jpg)

問題レポートは、販売・在庫・能力・製造の各メニューにあります。メニューごとに、表示される種類（需要・部品不足・能力・作業）が絞り込まれます。URL を `/problem/` にすると、すべてが出ます。

制約なし計画は、納期を満たす代わりに、実行できない前提をここに警告として並べます。能力オーバーが 1 件、というのが今回の結果です。

### 2. 製造オーダー・購入オーダー: 何を、いつ作る・買うかを見る

1. **製造** メニューの **製造オーダー**（Manufacturing orders）を開きます。`Make table` が 3 件並びます。
2. 「開始日」「終了日」の列を見ます。3 件とも `table`、`factory`、`Make table` で、開始日が 1 日ずつずれています。作業台は 1 台なのに、期間が重なっています。これが、先ほどの `overload` の原因です。
3. **購入** メニューの **購入オーダー**（Purchase orders）を開きます。`plank` 300 枚と `screw` 1200 本の 2 件が、`lumber shop` から出ています。
4. 「Ordering Date」（発注日。英語のまま）の列を見ます。plank の発注日は **基準日の 3 日前**、つまり過去の日付です。入荷（Receipt Date）を最初の製造に間に合わせるために、リードタイム 3 日を逆算した結果です。

![製造オーダー。Make table が 3 件、開始日が 1 日ずつずれて重なっている](/images/frepple-tutorial-ja/first-plan-manufacturing-orders.jpg)

![購入オーダー。plank の発注日（Ordering Date）は基準日の 3 日前になっている](/images/frepple-tutorial-ja/first-plan-purchase-orders.jpg)

:::message
plank の発注日が過去にならず、入荷日と同じ日になっていたら、5 章の商品供給者の「リードタイム」が `3`（3 秒）になっています。`3 00:00:00`（3 日）に直して、計画をやり直してください。
:::

一覧が横に長いときは、下のスクロールバーで右に動かします。「数量」「ステータス」の列は右側にあります。ステータスは、計画エンジンが出した提案なら `proposed`（提案済み）です。承認すると `approved`（承認済み）、確定すると `confirmed`（確認済み）になります。意味は 8 章で説明します。

### 3. 資源・棚卸・需要レポート: 負荷・部品・納品を見る

1. **能力** メニューの **資源レポート**（Resource report。`/resource/`）を開きます。最初はグラフで表示されます。
2. 右上のボタンのうち、左端の **テーブルを表示** を押します。期間ごとに「可能」（使える能力）、「負荷」、「稼働率 %」が並びます。
3. `workbench` の「稼働率 %」を見ます。**100% を超えた日は赤字** で表示されます。このモデルでは、116.67%、216.67%、300% と、3 つの製造が重なる日ほど高くなります。左の列の「稼働率 %」は、全期間の平均です。

![資源レポート（テーブル表示）。100% を超えた日の稼働率が赤字になっている](/images/frepple-tutorial-ja/first-plan-resource-report.jpg)

続けて、部品と受注の側も確かめます。

4. **在庫** メニューの **棚卸レポート**（Inventory report。`/buffer/`）を開き、同じく **テーブルを表示** にします。`plank` の行では、基準日の「Total produced」（入庫）が 300、その後 3 日間の「Total consumed」（出庫）が 100 ずつになっています。購入した板が、毎日の製造で使われていく様子です。
5. **販売** メニューの **需要レポート**（Demand report。`/demand/`）を開きます。3 件の受注はすべて納期どおりに満たされるので、不足も遅れも出ません。

期間別のレポートは、右上の時計のボタン（Set time horizon）で、表示する期間を変えられます。

予想と合っていたでしょうか。受注はすべて納期どおりに満たされます。しかし、作業台は 1 台しかないのに 3 つの製造が重なり、板の発注はすでに過去の日付です。つまり、現実には実行できない計画です。

## 制約なし計画とは

上の結果は、制約なし計画の性質そのものです。ERP の MRP（所要量計算）に近い計画で、次の特徴があります。

- **すべての受注が納期どおりに満たされます。**
- そのために、機械の能力を超えて仕事を詰め込んだり、過去の日付に製造・購買を計画したりします。
- 「部品が足りない」「能力が足りない」といった問題は、**問題レポート** で警告として示されます。

つまり「理想的にはこう作りたい」という計画で、実行可能かどうかは別の話です。現実に守れる計画（制約あり計画）は 7 章で作ります。

### 供給経路をたどる（供給パス / 使用場所）

品目・受注・リソースなどの画面には、その行のコンテキストメニューがあります（行の横のアイコンをクリックします）。そこから **供給パス**（supply path。その品目がどこから供給されるか）や **使用場所**（where used。その品目がどこで使われるか）を開けます。`table` の供給パスをたどると、`Make table` で作り、材料の plank と screw は lumber shop から購入する、という流れが見えるはずです。

## レポートの URL 早見表

| レポート | メニュー | URL |
|---|---|---|
| 問題レポート（problem report） | 販売・在庫・能力・製造 | `/problem/`（メニューごとに `?entity=…` で絞り込み） |
| 製造オーダー | 製造 | `/data/input/manufacturingorder/` |
| 購入オーダー | 購入 | `/data/input/purchaseorder/` |
| 資源レポート（resource report） | 能力 | `/resource/` |
| 需要レポート（demand report） | 販売 | `/demand/` |
| 棚卸レポート（inventory report） | 在庫 | `/buffer/` |
| 条件レポート（constraint report） | 販売 | `/constraint/`（7 章で使う） |

## つまずきポイント

- 購入オーダーが 1 件も出ない: 「サプライチェーンを生成」のチェックが外れていないか確認してください。商品供給者の「商品」と「地域」が合っているかも確認してください。
- 計画しても何も出ない: 商品 `table` に、補充する手段（作業の「商品」が `table` で「地域」が `factory`）が登録されているかを確認してください。問題レポートに「invalid data」が出ている場合は、補充手段が「ない」「多すぎる」のどちらかです。
- `plan.sh` が `Done` にならない: 実行画面の「タスクの状態」（Task status）で、そのタスクの状態とログ（「表示」）を確認してください。
- レポートが空になる: 表示期間が計画の範囲から外れている可能性があります。計画基準日は「今日」です。画面上部の期間が基準日を含んでいるか確認してください。
- 英語の用語が分かりにくい: `buffer`（バッファ）は「品目×拠点」の在庫の単位、`operation`（作業）は工程、`demand`（需要）は受注（または予測）のことです。
