この章のゴール: 5 章のモデルで最初の計画（制約なし）を作り、各レポートで結果を読めるようになる。

:::message
**この章で学べる計画の考え方**

- 制約なし計画は MRP（受注から、必要な部品・製造・購買の量とタイミングを逆算する計算）に近く、すべての受注を納期どおりに満たす計画になる
- 実行できるかどうかは、問題（警告）として別に示される
- 計画は、需要・在庫・能力・例外の 4 つの視点で検証する
:::

## 計画を生成する

Admin メニューの **Execute** を開き、「Create a plan（計画を作成）」カードを使います。まずは違いを体感するために、**制約なし** で実行します。

1. 「Planning steps」で「Generate supply plan（日本語表示では「サプライチェーンを生成」）」にチェックが入っていることを確認します。これがオフだと、購買オーダー（PO）などの供給計画が生成されません。（「Generate forecast」は需要予測の機能です。13 章で扱うので、いまはオフのままにします。）
2. 「Plan type」で「Unconstrained plan」を選びます。
3. 「Constraints」の 3 つ（Capacity / Manufacturing lead time / Purchasing lead time）は、すべてオフにします。
4. `Launch`（日本語表示では「起動」）を押します。

![Execute 画面の「Create a plan」カード](/images/frepple-tutorial-ja/execute-create-plan.jpg)

計画の生成は、このモデルなら数秒で終わります。画面上部のステータス欄が `Done` になれば完了です。タスクは非同期に実行され、ステータス欄は 5 秒ごとに更新されます。

### コマンドで実行する（任意）

画面の代わりに Web API でも、同じ計画を実行できます。以降の章では、繰り返し実行するので、この方法を使います。

```bash
cd examples/frepple-api
./plan.sh "plantype=2&constraint=0&env=supply"
# task 6: Done (6s)
```

`plan.sh` は Web API（`POST /execute/api/runplan/`）を呼び、終わるまで待つスクリプトです。クエリの意味は次のとおりです。

| パラメータ | 意味 |
|---|---|
| `plantype=2` | 制約なし計画（1 なら制約あり計画） |
| `constraint=0` | 制約をすべてオフ。オンにするときは `capa,mfg_lt,po_lt` のように書く |
| `env=supply` | 「Generate supply plan」に対応 |

:::message
`docker exec … frepplectl runplan` でも計画は実行できますが、9.17.0 では計画が終わってもコマンドが戻ってきません。この本では使いません。
:::

## 制約なし計画とは

制約なし計画は、ERP の MRP（所要量計算）に近い計画です。

- **すべての受注が納期どおりに満たされます。**
- そのために、機械の能力を超えて仕事を詰め込んだり、過去の日付に製造・購買を計画したりします。
- 「部品が足りない」「能力が足りない」といった問題は、**問題レポート** で警告として示されます。

つまり「理想的にはこう作りたい」という計画で、実行可能かどうかは別の話です。現実に守れる計画（制約あり計画）は 7 章で作ります。

## 生成された計画の中身

計画エンジンは、次のオーダーを出力します。

| 出力 | 内容 |
|---|---|
| 製造オーダー（MO） | 何を、いつからいつまで、いくつ作るか |
| 購買オーダー（PO） | 何を、どのサプライヤーから、いつ、いくつ買うか |
| 配送オーダー（DO） | 拠点間で何をいつ運ぶか（10 章で扱います） |
| 納品（DLVR） | 受注ごとの出荷 |

5 章のモデルでは、次のようになりました（手元の環境で実測した値です。計画基準日は実行日なので、日付は実行する日で変わります）。

| 見るところ | 結果 |
|---|---|
| 製造オーダー | `Make table` が 100 個ずつ 3 件。作業台 1 台なのに、開始が 1 日ずつしかずれず、期間が重なっている |
| 購買オーダー | plank 300 枚、screw 1200 本の 2 件。**開始が過去の日付**（基準日の 3 日前）になっている |
| problem report | workbench の `overload`（能力オーバー）が 1 件 |

予想と合っていたでしょうか。作業台は 1 台しかないのに、3 つの製造が重なって計画されています。板の発注も、すでに過去の日付です。受注はすべて納期どおりに満たされますが、現実には実行できません。

それぞれのオーダーは status を持ちます。計画エンジンが出した提案は `proposed` です。プランナーが承認したものは `approved`、実行が確定したものは `confirmed` になります。status の意味は 8 章で説明します。

## レポートで結果を検証する

メニュー名は画面の言語設定で変わります。ここでは英語表記で書き、括弧内に URL を添えます。迷ったら、`http://localhost:9000` に続けて URL を直接入力しても開けます。

| レポート | URL | 分かること |
|---|---|---|
| demand report | `/demand/` | 受注ごとの、納品量・遅れ・不足 |
| inventory report | `/buffer/` | 品目×拠点ごとの在庫の推移 |
| resource report | `/resource/` | リソースごとの負荷率 |
| problem report | `/problem/` | 計画上の問題（能力オーバー、部品不足など） |
| constraint report | `/constraint/` | 受注が遅れた・不足した理由（7 章で使う） |

期間別のレポートは、画面上部で表示する期間の単位（日・週・月など）や範囲を変えられます。

### 1. 需要レポート（Sales メニューの Demand report）

期間ごとに、受注の数量（demand）と、計画で納品される数量（supply）が並びます。制約なし計画では、3 件の受注はすべて納期どおりに満たされるので、不足も遅れも出ません。7 章の制約あり計画で、ここが変わります。

### 2. 在庫レポート（Inventory メニューの Inventory report）

品目と拠点の組み合わせごとに、期首在庫・入庫・出庫・期末在庫が期間別に出ます。「この部品はいつ入荷して、いつ使われるのか」を追うのに使います。`plank` を選び、購買オーダーの入庫が、製造オーダーの出庫より前にあるかを確認してみましょう。制約なし計画では、入庫のほうが過去の日付になっています。

### 3. リソースレポート（Capacity メニューの Resource report）

リソースごとに、期間別の使用可能な能力（available）と負荷（load）、負荷率（utilization）が表示されます。

- 負荷率が **100% を超える** 期間は、能力オーバーです。
- 制約なし計画では、`workbench` の負荷率が 100% を超えます。3 つの製造が同じ作業台に重なっているためです。
- 制約あり計画（7 章）では、100% を超えないように仕事が後ろにずらされます。

### 4. 問題レポート（Problem report）

制約なし計画では、「能力が足りない」「部品が足りない」といった問題が、ここに **警告として** 並びます。計画自体は納期を満たしているので、その代わりに「現実にはこの前提が崩れる」ことを教えてくれるわけです。

主な問題の種類は次のとおりです。

| 対象 | 問題 |
|---|---|
| Resource | overload（能力オーバー） |
| Buffer | material shortage（部品・在庫の不足）、invalid data（補充手段がない／多すぎる） |
| Operation | precedence（工程の前後関係が守られていない） |
| Demand | invalid data（計画できないデータ不備） |

### 5. 供給経路をたどる（Supply path / Where used）

品目・受注・リソースなどの画面には、その行のコンテキストメニューがあります（行の横のアイコンをクリックします）。そこから **supply path**（その品目がどこから供給されるか）や **where used**（その品目がどこで使われるか）を開けます。

`table` の supply path をたどると、`Make table` で作り、材料の plank と screw は lumber shop から購入する、という流れが見えるはずです。

## つまずきポイント

- 購買オーダーが 1 件も出ない: 「Generate supply plan」のチェックが外れていないか確認してください。item supplier の item と location が合っているかも確認してください。
- 計画しても何も出ない: item の `table` に、補充する手段（工程の `item` が `table` で `location` が `factory`）が登録されているかを確認してください。problem report に「invalid data」が出ている場合は、補充手段が「ない」「多すぎる」のどちらかです。
- `plan.sh` が `Done` にならない: Execute 画面の Task status で、そのタスクの状態とログ（View）を確認してください。
- レポートが空になる: 表示期間が計画の範囲から外れている可能性があります。計画基準日は「今日」です。画面上部の期間が基準日を含んでいるか確認してください。
- 英語の用語が分かりにくい: `buffer` は「品目×拠点」の在庫の単位、`operation` は工程、`demand` は受注（または予測）のことです。
