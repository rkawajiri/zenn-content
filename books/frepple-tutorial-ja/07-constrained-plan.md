---
title: "制約あり計画"
---

この章のゴール: 制約あり（有限能力）の計画を作り、制約なし計画との違いと、受注が遅れる理由・ボトルネックを読み取れるようになる。

:::message
**この章で学べる計画の考え方**

- 制約の種類（能力・製造リードタイム・調達リードタイム）と、それぞれが何を守るか
- 守れなかった分は「問題」ではなく「受注の遅れ」として現れる
- 遅れの理由をたどり、ボトルネックを特定する考え方
:::

## 制約あり計画とは

6 章の制約なし計画は、「すべての受注を納期どおりに」を最優先にして、能力オーバーや過去日付のオーダーを許しました。一方、**制約あり計画** は、守るべき制約を守り、その範囲でできるだけ納期に近づけます。守れない分は、受注を **遅らせる** か **一部を出荷しない（不足）** ことで表現します。

frePPLe で選べる制約は 3 つあります。

| 制約 | 意味 |
|---|---|
| Capacity | リソースの能力を超えない |
| Manufacturing lead time | 製造・配送オーダーを、計画基準日より前（過去）に開始・終了しない |
| Purchasing lead time | 購買オーダーを、計画基準日より前（過去）に開始・終了しない |

:::message
「confirmed」のオーダーだけは、過去の日付でも許されます（すでに実行に移した、と見なされるためです）。`proposed` と `approved` のオーダーは、必ず未来になります。
:::

## 制約あり計画を実行する

Execute 画面の「Create a plan」カードで、次のように設定します。

1. 「Generate supply plan」にチェックを入れる。
2. Plan type は「**Constrained plan**」を選ぶ。
3. Constraints は 3 つとも **オン**。
4. `Launch` を押す。

Web API なら、次のとおりです。

```bash
./plan.sh "plantype=1&constraint=capa,mfg_lt,po_lt&env=supply"
```

## 制約なし計画との比較

6 章の予想と見比べてください。以下は、手元の環境で実測した値です（日付は実行する日で変わります）。

| 見るところ | 制約なし計画 | 制約あり計画 |
|---|---|---|
| problem report | workbench の `overload` が 1 件 | 問題なし |
| 納品日 | 納期どおり | order 1 は納期より 3 日遅れ、order 2 は 5 日遅れ、order 3 は 8 日遅れ |
| 製造オーダー | `Make table` が 100 個ずつ 3 件、期間が重なる | 26 件に分かれ、作業台が空く順に並ぶ |
| 購買オーダー | 開始が過去の日付 | plank は合計 300 枚、screw は合計 1200 本。いずれも未来の日付 |

制約あり計画で問題がなくなったのは、制約を守れるように計画を組み直した結果です。守れなかった分は、問題としてではなく「受注の遅れ」として現れます。

後ろの受注ほど大きく遅れるのは、作業台が 1 台しかなく、順番に作るしかないためです。制約なしでは購買オーダーが過去の日付に出ますが、制約ありでは板の到着（D0 + 3 日）を待ってから製造を始めます。

Sales orders の一覧には **Delay** 列があり、納期に対する遅れが赤いセルで出ます。この列は日数を切り上げるため、納品日の差より 1 日大きく出ることがあります。

## 遅れの理由を調べる（constraint report）

Sales メニューの **Constraint report**（`/constraint/`）を開きます。遅れた受注と、その理由が並びます。

このモデルでは、各受注に次の理由が並びます。

| 理由（name） | 意味 |
|---|---|
| overload | リソースの能力が足りなかった（`workbench`） |
| manufacturing lead time | 製造を始めるべき日がすでに過去だった（`Make table`） |
| purchasing lead time | 購買を発注すべき日がすでに過去だった（`Purchase plank ...`） |

「なぜこの受注は遅れたのか」を 1 件ずつ説明できるようになるのがゴールです。たとえば order 1 は、板が届くまで 3 日待たされ（購買リードタイム）、そのうえ作業台が空くのを待った（能力）、と読めます。

:::message
`overload` は「ある時点で能力が足りなかった」ことを示すだけで、最終的な遅れの大きさは表しません。
:::

## ボトルネックを見つける

ボトルネックは、全体の進み方を決めている、もっとも余裕のない資源です。次の手順で探します。

1. constraint report で、`overload` の行を探す。
2. その行の owner 列（能力が足りなかったリソース）を見る。同じリソースに多くの受注が集中していれば、それがボトルネックです。このモデルでは `workbench` です。
3. Capacity メニューの **Resource report** で、そのリソースの負荷率が高い期間を確認する。

## 考えてみよう

制約の効果を実感するために、3 つの制約を 1 つずつ外して実行し、遅れる受注がどう変わるかを予想してから確かめてみましょう。

| パターン | `constraint` |
|---|---|
| A. 能力だけ | `capa` |
| B. リードタイムだけ | `mfg_lt,po_lt` |
| C. 全部 | `capa,mfg_lt,po_lt` |

```bash
./plan.sh "plantype=1&constraint=capa&env=supply"
```

12 章のデモデータでは、遅れの主な原因は能力ではなくリードタイムでした。どんなデータだと、能力が主な原因になるのかを考えてみましょう。

:::message
実行するたびに計画は上書きされます。結果を残したいときは、Excel にエクスポートするか、9 章の What-if シナリオにコピーして比較します。
:::

## つまずきポイント

- 制約あり計画にしても遅れが出ない: 制約のチェックが外れていないか、Plan type が「Constrained plan」になっているかを確認してください。
- constraint report が空: 制約なし計画では空になります。制約あり計画を実行した後で見てください。
- 数字が本文と違う: 日付や frePPLe のバージョンで変わります。傾向を確認してください。
